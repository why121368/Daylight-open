1. 目标与方法学

1.1 要回答的问题（不是「跑个分」）

  1. 把依赖层与应用层都换成自带复制/选主的组件后，故障面是否真的变小了： 单 Pod、单节点、控制面 1/3、整个可用区分别下线时，用户看到什么？
  2. 跨 AZ 是结构性保证还是碰巧：副本/依赖实例的分布是否被强制打散，而不是概率事件？
  3. 弹性伸缩在真实指标（CPU）驱动下是否发生，扩容的收益与代价各是多少？
  4. 容量上限由哪个模块决定（逐模块归因），而不是给一个笼统的 QPS。

1.2 判定口径（可复算，不靠形容词）

  • QPS = 样本数 ÷（首个样本开始 → 末个样本结束）的墙钟秒数；分位数取 nearest-rank。
  • 成功 QPS = QPS × (1 − 错误率)；错误率以 JMeter .jtl 的 success 列为准。
  • 故障期错误窗口 = 探针侧「第一个非 2xx」到「最后一个非 2xx」之间的墙钟长度（不是注入到恢复的时长）。
  • ready 掉线 = /health/ready 返回非 200 的时长。
  • 所有原始产物（JMeter .jtl、探针 CSV、HPA 时间序列、组件面证据）都留在结果目录里，报告只做解析与并排，不重新"美化"数字。

1.3 与生产环境的已知偏差（必须明说）

偏差 影响 为什么不修
压测令牌是后端密钥自签 JWT，不带 jti 少一次会话行更新；其余鉴权路径（查库、会话版本校验）都被真实覆盖 登录接口强制图形验证码，无法脚本化；与 compose 档同口径
入口是压测机（node-03）上的 nginx，不是云 SLB/Ingress 入口本身是单点（但挂了会立刻暴露，见 §5） 客观条件；报告如实标注
明文 HTTP，无域名/证书 无 TLS 开销 未验证项，见 §10
公网 5 Mbps，全部负载走私网 压测流量与业务流量不走同一条公网链路 规避公网瓶颈，两档一致
对象存储 MinIO 单实例 附件路径不具 HA（唯一非 HA 组件） 7 台机器凑不出纠删码盘组，见 §10

4. 依赖层：自带复制与自动主从切换（实测）

三组依赖都由组件自身完成复制与选主，应用只改三个连接串（§2.2）。下面每一条都能在对应故障目录的 component-inject.txt / component-after.txt 里找到原文。

4.1 PostgreSQL（CloudNativePG，1 主 2 备，跨 3 区强制打散）

  • 注入前：INSTANCES 3 / READY 3；删掉主库 Pod（daylight-pg-1）后立即快照：READY 2；
  • 恢复后：INSTANCES 3 / READY 3，PRIMARY 已从 daylight-pg-1 变成 daylight-pg-2（提升确实发生了）；
  • 业务侧：探针首个错误到首个恢复 2xx 之间隔 4.9s，daylight-pg-rw 端点自动改指新主；
  • 但探针错误跨度是 197.2s、并发负载失败率 82.71%（其中 502 有 10521 个）—— 放大这次故障的不是 PG，而是应用（§5.1 的两个缺陷）。

4.2 Redis（3 数据节点 + 3 Sentinel + 2 HAProxy，各组分属不同区）

  • 注入对象是 Sentinel 报告的当前主库：日志原文 pod "daylight-redis-0" deleted；
  • 恢复后 Sentinel 视角的主库是 10.42.7.13（daylight-redis-2，node-07）→ 主库身份确实切换了； 3 个 Sentinel 全程 Running；
  • 业务侧：探针 51 次请求 0 失败（错误码分布为空），ready 掉线 0.9s —— 说明 HAProxy 把连接改道到新主，抖动被代理层吸收，没有传到业务路径。

4.3 RabbitMQ（3 节点 + quorum 队列）

  • 注入对象：daylight-rabbitmq-2；恢复后它重新 Running（新 IP 10.42.3.18）， 而 rabbitmq-0 / rabbitmq-1 全程没有重启（uptime 连号）→ 任何时刻都有 2/3 存活；
  • 业务侧：探针 193 次请求 0 失败，ready 未掉线。
  • 口径提示：探针只打 /api/state（读路径），不经过队列；所以这一项证明的是 "节点挂掉时业务读路径不受影响"，不是"队列消息没丢"。消息不丢需要单独做投递-消费计数（未做）。

4.4 MinIO（单实例，明确的非 HA）

  • daylight-minio-0 是单实例，删掉就是整体不可用；本轮只验证了"删它不会连带打挂读路径" （探针 174 次 0 失败），附件下载/上传在这段时间不可用没有被测（探针不经过附件路径）。
  • 升级路径（未做）：MinIO 分布式纠删码，或改用云对象存储。7 台机器凑不出纠删码盘组，见 §10。

4.5 被实测推翻的预设：删 PG 主库 + 1 备库

  • 扩到 9 副本的代价：API 层 3 → 9 个 Pod（每 Pod 峰值 1.29 核 / 922Mi）， 即约 +6 核 / +4 GiB 的瞬时资源；HPA 上限 9 是当前的硬顶（再高的负载只能是排队）。
  • 缩容：撤压后 CPU 降到 1%，副本回落（本档采样窗口内到 4，集群侧复核最终 3/3）。

7. 容量档

7.1 本节口径（先说清楚，再看数）

  • 固定 3 副本测的：测量前把 daylight-api 的 HPA min=max=3（否则量到的是"带自动扩缩的容量"）， 测完还原成 min=3/max=9（实测还原成功）；worker 不动。

  3. 去掉 LB 后 node-03 仍钉在 99%，剩余上限是压测源自己（单 JMeter JVM 峰值吃满 4.0 核）。 所以本轮测不到系统天花板，只能给下界。

顺带纠正一条旧说法：state-all@100 的 52 QPS 也不是应用「拼不出响应」—— 同一档应用侧 CPU 只有 1.8%（峰值 9.3%），而它的响应体是 3.34 MB， 52 × 3.34 MB = 175 MB/s，同样落在上面那条「每 MB ≈ 6.9 ms」的字节预算里。 即：本轮 state 与 state-all 两个数字都是被测量链路压出来的下界， 不能用来判断 scope=all 到底能不能优化 —— 要判它必须先把响应体降下来（投影/分页）再测。

因此本轮容量的口径只有一句话：≥ 920 成功 QPS @3 副本（直连 NodePort，错误 0%）； 与基线可横向比较的是同入口的 594.1（+32×）。两个数字都必须带入口说明，否则不可比。

新增三条缺陷记在 §11（20 校验池未采埋点、21 压测源与被测链路共用节点）。

10. 局限与未验证项（不美化）

  1. MinIO 单实例：附件路径不具 HA，故障矩阵第 8 项会失败，这是如实记录而不是通过。
  2. local-path 本地盘：PG 的卷绑定在首次调度的节点上；该节点彻底死掉时，实例会在同区另一节点上重建，但旧卷不会漂移（数据来自副本同步）。生产应换复制型存储（Longhorn/Ceph 列为可选，未启用）。
  3. 依赖层的多数派是 3：同时丢 2/3 写入不可用（第 9 项），这是 3 副本的物理边界，不是 bug。
  4. 入口是压测机上的 nginx：不是云 SLB；它所在的节点故障会让入口一起消失（本档把它放在 az-i 并只做 node-kill，不参与整区下线）。
  5. 公网 HTTPS / 域名 / 证书未验证（当前为明文 HTTP）。
  6. 真校园邮箱不可达：Coremail 反垃圾拒收校园语料邮件，本地校园 IMAP 不可靠 → 真实收发链路的云端验证仍缺。
  7. 只有一个可用区做过整区下线（az-b）；az-j 作为补充用例（§3 命令），结果同样如实记录。 az-i 没测、也测不了：PG 主库、控制面节点、入口 LB 与压测机都在 az-i，把整区打掉会连带毁掉测量链路本身， 得到的是「连不上」而不是「系统怎么反应」。所以「整区挂了仍服务」这句话在本档只对 az-b 成立， 对 az-i（主库所在区）是未验证，不能外推。
  8. 「7 台 / 3 AZ」之外的分区容灾（跨 region、跨 VPC）未验证。
  9. NodePort 对公网暴露：实测 http://<任意节点公网 IP>:30080/health/ready 全部返回 200， 也就是 7 台机器各有 1 份应用入口。控制台侧的安全组没有权限改，已作为待办交付 （work/enterprise-acceptance/P4-nodeport.md，含集群侧收口脚本）。这属于网络面未收口，不是已完成项。
  10. 依赖层没有退到「数据节点单机」形态：冻结稿把 PG/Redis/MQ 放在 test-01， 本次按用户决策保留跨可用区多副本（否则 az-i 一挂业务全停，与第 7 条的结论矛盾）。 这是与冻结稿的唯一形态差异，取舍理由见 work/enterprise-acceptance/RUNBOOK.md。
  11. 控制面节点是 node-01/04/06，不是冻结稿写的 02/04/06：两者都跨 3 个可用区，可用区级容灾性质等价； 重排需要卸载/重装 k3s（会打掉 node-02 上的 PG 主库），在没有额外容灾收益的前提下只增加风险，故未做。
  12. 本轮容量数字是下界，不是系统天花板（缺陷 21）：压测机 node-03 同时住着 JMeter、nginx LB 和 Prometheus， 只有 4 核；state@100 走 LB 得 594 QPS 时该机整机 CPU 已 99%（JMeter 单进程峰值 4.0 核）， 绕开 LB 直打 NodePort 拿到 920 QPS 时仍是 99%。因此只能写成 「≥ 920 成功 QPS @3 副本（直连入口）；同入口同口径 ≥ 594」， 不得表述成「系统上限 594 / 920 QPS」（§7.4）。

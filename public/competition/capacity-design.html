1. 决定设计的三条实测事实

# 事实 实测数字 出处
1 应用不是瓶颈（缓存命中路径） 3 副本合计 CPU 均值 0.24–0.38 核（峰值 1.04/3 核）；应用内在途请求均值 3.56 / 峰值 24（客户端压 50–200 线程）；服务端 p50 8.4 ms 三档不涨 REPORT §7.4
2 瓶颈是「响应体字节 × 搬运次数」，落脚在入口与压测源 health（366 B）@同机 2051 QPS；state（175 KB）594；绕开 nginx LB 直打 NodePort 920（+55%）；此时 node-03（4 核，同时跑 JMeter + nginx LB + Prometheus）整机 CPU 99%、nginx 峰值 2.3 核 REPORT §7.4 天花板定位
3 读缓存已经把「每次整份装配」消掉了，但只在单进程内 40 527 个请求全部 result=hit（miss/stale/unavailable 各 0）；整轮仅 166 次快照 REPORT §7.4 缓存证据

补充两条与「容错」直接相关的实测（基线故障矩阵）： 跨区（az-b）整区下线只丢 3/40 个探针请求；控制面 3→2 丢 4/32；删 1 个 api Pod 首次中断 12.9 s（偏长，见 §5.2）； PG 主库被删后 CNPG 自动提升、首次中断 4.9 s（REPORT §5、§6）。

从这三条事实推出的设计结论（先给结论）

  1. 3k 在 7 台内可行，但有一个硬前提：响应体从 175 KB 降到 ≤20 KB。 否则 3k × 175 KB = 525 MB/s，按改造前实测的入口成本（594 QPS 吃 2.3 核，且入口与压测机同机抢 CPU） 线性外推需要 ~11.6 核只用来搬字节 —— 相当于 3 台节点的全部 CPU 什么都不干只做搬运，不可行。 降到 20 KB 后总量 60 MB/s，入口只要 ~1.2 核。 本轮落地入口层后这条结论没有变：同口径主读路径（175 KB）已到 1018 成功 QPS（REPORT §7.5）， 但 state-all（3.34 MB）在两种入口下都卡在 ~60 QPS —— 字节量才是那条路的约束。
  2. 入口层必须从「压测机上的单容器」变成「跨区多副本」，且压测源与入口彻底分开。 改造前：入口 nginx 与 JMeter、Prometheus 挤在 node-03 上，整机 99% 时既是 SPOF 又是吞吐上限（实测）。 本轮已落地（3 副本跨 3 区，形态见 §4.2、验收见 §4.3）：同口径 589 → 1018 成功 QPS（1.73×）， p50 65 → 27 ms；负载下删 1 个入口副本探针 0/222 失败。详见 REPORT §7.5。
  3. API 副本不需要多：按 §3 公式，3k 只需 3–6 个副本；加副本解决不了字节问题，只会加连接。
  4. 容错缺口只有三块（其余已有）：调度器单副本、MinIO 单实例的附件语义、PG 卷是 local-path（节点本地盘）的备份恢复。

2. 容量模型（可复算，改完要用同一把尺子复测）

2.1 公式

所需 API 副本数   = ceil( 峰值QPS × 单请求CPU秒 / (单副本CPU上限 × 目标利用率) )
所需入口副本数    = ceil( 峰值QPS × 单请求入口CPU秒 / (单节点可用核 × 目标利用率) )
PG 连接上限约束   = maxReplicas × (业务池 + 校验池 + 探针) + 后台任务预留 ≤ PG max_connections

4. 入口层设计（P0，本轮最痛的一处）

4.1 现状问题（都有实测）

  1. 单实例：入口 nginx 是 node-03 上的一个容器 → SPOF；
  2. 与 JMeter、Prometheus 同机 4 核 → 实测峰值 2.3 核，整机 99%，state 档 QPS 卡在 594；
  3. 绕开它直打 NodePort，+55%（594 → 920） —— 说明它自己就是瓶颈；
  4. 两处入口的重试策略是两种相反的毛病（这里先前写反了，已按实测更正）：
  5. 容器 LB（压测装置）：proxy_next_upstream error timeout，端点被摘空时直接 502，没有跨副本兜底；
  6. 公网边缘 nginx（node-07，真正的用户入口）：proxy_next_upstream error timeout http_502 http_503 http_504
    • max_fails=2 fail_timeout=5s + worker_connections 768。这一条才是历史上刷出 78221 个 502 的成因： 应用的 503 语义是「过载背压，可重试，带 Retry-After」，一旦被当成上游故障，nginx 就把每个请求 放大成 3 次上游尝试，并按 max_fails 把 3 个上游逐个摘除，最后在 no live upstreams 状态 对所有请求秒回 502 —— 故障被从「一个后端过载」放大成「入口全体不可用」。 所以「让入口能兜底」的正确做法不是放开 502/503 重试，而是①上游健康判定交给 k8s readiness， ②入口自身多副本跨区，③入口不设 max_fails 被动摘除（见 §4.2）。

4.2 实际落地的形态（work/cloud-perf/k3s/manifests/15-ingress.yaml）

入口从「node-03 上的单容器」变成「集群内 3 副本 Deployment + NodePort 30081」， 不新增机器、不动安全组（公网仍只从 node-07 进）。逐条对应上面的四个问题：

设计点 落地做法 为什么这样做
3 副本跨 3 区（不是单实例） Deployment replicas: 3 + topologySpreadConstraints{topologyKey: daylight.dev/zone, whenUnsatisfiable: DoNotSchedule, maxSkew: 1}，加 PodDisruptionBudget{minAvailable: 2} 让「打掉一个区最多损失 1/3 入口」是结构性保证，不是调度器碰巧这么放；DoNotSchedule 保证宁可 Pending 也不挤在同一个区
上游不再写死节点 IP upstream daylight_api { server daylight-api:3000 }（ClusterIP，kube-proxy 维护 endpoint 集合） 节点 IP 不进配置；Pod 不健康由 k8s 自动摘除，不再依赖 nginx 的被动健康检查
健康判定归 readiness，不归 nginx max_fails=0（关闭被动健康检查）+ 上游只留 error timeout 重试 根因见 §4.1 第 4 条：max_fails + 重试 503 会把上游逐个摘空。503 是背压语义，必须原样透传给客户端（带 Retry-After），不能当成上游故障
大响应体不落磁盘 listen 8080；proxy_buffer_size 16k / proxy_buffers 16 32k / proxy_busy_buffers_size 64k；worker_connections 16384；upstream keepalive 64 175 KB（列表）/ 3.3 MB（混合视图）的响应若被默认 8×4k 缓冲推到临时文件，入口就变成磁盘队列（与实测「每 MB 6.9 ms」同形）。keepalive 复用后端连接，省掉每请求三次握手
入口可自证（可观测） location = /lb-health { return 200 'ok'; }（不经过后端）+ add_header X-Daylight-Ingress $hostname always + access_log off（压测期不写盘）/ error_log /dev/stderr warn /lb-health 供 k8s 探针与巡检；响应头用来证明「请求真的散布在多个入口副本上」（本轮验收就靠它）
满足 restricted 安全策略 runAsNonRoot + runAsUser/Group/fsGroup: 101 + seccompProfile: RuntimeDefault + capabilities.drop: [ALL] + allowPrivilegeEscalation: false + 配置/pid/cache 全部走 emptyDir 命名空间是 enforce=baseline、warn/audit=restricted。dropping ALL caps 后绑不上特权端口 80，所以副本内部听 8080，对外由 Service 把 80→8080（标准无特权写法）
故障切换要能在分钟级观察到 terminationGracePeriodSeconds: 30 + preStop: sleep 5（先摘端点再退出）+ 驱逐容忍 tolerationSeconds: 60 默认 300s 的驱逐时限太长，演练里看不到切换；preStop 消掉「端点已摘、连接还在打」的窗口
压测源与入口彻底分开 入口副本与压测机不同机；容量档期间 cordon node-03 并把落在它上面的 api 副本重排走 node-03 让给 JMeter + Prometheus，它不再在测量链路上

资源按「实测成本」给：requests 500m / limits 2 核。2 核上限是因为实测 594 QPS@175 KB 时入口吃 2.3 核 （每请求 ≈3.9 ms），给足了才不会在大响应档被 CFS 配额掐死；投影到 20 KB 量级后应再回调（§3 容量公式）。

A2 ~~不要在持连接期间做装配~~ （核对后：已修，不是待修项） createStorageSnapshot 在 finally 里就 client.release()，路由装配发生在释放之后（server/storage/index.js）。真正测到的是快照装载成本：storage.snapshot.ms p50 80.7 ms / p95 425.5 ms / max 652.7 ms（整轮仅 166 次，即只有缓存未命中才付） 待改的是「装载时长」与「每个副本各自冷启动」，不是装配 见下方 A2′
A3 共享读缓存（Redis）+ 校验池埋点（埋点已落地：pg.validation.*） 缓存 100% 命中但只在单进程内；新 Pod 冷启动要重装；校验池原先没埋点（缺陷 20） 冷启动不打库；跨副本共享热数据；校验成本可测 Redis 往返（~0.2 ms）+ 失效协议

A2′ 才是真正剩下的那一项（原文把问题定位错了，这里更正）：冷路径的成本不在"装配时占着连接"， 而在每次未命中都要重新装载一份完整快照——p50 80.7 ms、p95 425.5 ms，且这期间占一条业务连接。 3 副本 × 8 连接的池，在 p95 装载时长下每秒只能支撑约 19 次冷装载。 所以正确改法是：① A3 共享缓存（让"冷"只发生一次，而不是每个副本各一次）； ② 减小被装载的数据量（列表投影同样作用于装载层，而不是只作用于响应体）。 「持连接做装配」这条已在 215ce86 修掉，不再列为待办。

5.2 首次中断时间要压下来

实测「删 1 个 api Pod，首次中断 12.9 s」偏长。清单里已有 preStop: sleep 8（先摘端点再退出）， 但仍出现秒级中断，说明端点摘除与连接排空的时序还没对齐。设计：

  • preStop 改为「先让 /health/ready 返回 503（draining）→ 等 2 个探针周期 → sleep」， 而不是固定 sleep 8：让「摘除」这件事由探针驱动，不靠猜时间；
  • 应用在收到 SIGTERM 后拒绝新请求但仍服务在途请求（现在有没有做要验）， terminationGracePeriodSeconds: 90 保持；
  • 验收：重复 5 次删 Pod，首次中断时间 < 1 s，错误率 < 1%（现在是 12.9 s）。

9. 测量装置也要一并设计（否则 3k 无法被证明）

实测：node-03（4 核）在 366 B 响应下最多 2051 QPS，175 KB 下 920 QPS。 要证明 3k，压测源本身必须能产生 3k，而它现在只有一个 4 核 JVM。

  • 不加机器的做法：把 JMeter 跑成分布式（现有节点做 remote server，例如 node-03 + node-01， 仅测量期间占用），汇总到同一份 JTL；
  • 口径不变（同并发、同时长、同入口），入口必须与基线同口径（否则 594 与 920 不可横比——已写进 REPORT §7.4）；
  • 顺手修三个测量缺口（都写进 REPORT §11）：校验池埋点（缺陷 20）、 run-meta.json 的 provenance 要读 ConfigMap 而不是本机 git（缺陷 16 同类）、 summary.md 的档位模板（缺陷 16）。

12. 明确不宣称（写下来是为了不改口径）

  • 不宣称生产就绪：本设计是在 7 台、3 个可用区、自建 k3s 范围内的目标形态； 跨 region、跨 VPC、公网 HTTPS/域名/证书、公网入口收口（安全组无权限改）仍是未验证项。
  • 不宣称 3k 已达成：3k 是目标，P1 之后才有实测数字；本轮已把同口径主读路径从 589 提到 1018 成功 QPS（1.73×，投影档 1042），且瓶颈已不在应用与入口 —— 但这仍是下界： 压测源（node-03，4 核）仍与 Prometheus 同机、单 JVM，state 档下它自己接近打满 （health/小响应体档实测 1955–2051 QPS 才是它的上限）。所以只能写 「≥1018（新入口 3 副本跨 3 区）/ ≥594（旧入口同口径）」，不得写「系统天花板 1018」。
  • 不宣称入口层是生产入口：本轮落地的是「3 副本跨 3 区 + PDB + ClusterIP 上游」的最小可用形态， 没有 HTTPS 终结、没有 WAF/限流、没有入口自身的 SLO 与容量水位告警；公网仍只有 HTTP。
  • 不宣称延迟 SLO 达标：SLO 数值（目标 p95、错误率、RTO/RPO）需要在 P1 之后按实测固定， 现在写下来就是凭空给数（符合 roadmap §4「不得凭空给出已达标的数字」）。
  • 不宣称依赖层高可用已完整：MinIO 单实例与 local-path 卷是明确的非 HA，如实保留。

# Daylight 云上容量与故障测试报告（k8s 真分布式档）

> 本文件记录 **k8s 档**（7 台 / 3 个真实可用区 / 控制面 3 server 的 k3s 集群）的测试方法与实测结果。
> 与 compose 档的分档对照见 `work/cloud-perf/COMPARISON.md`。
> 状态口径（本文严格区分）：**规划中 / 代码已实现 / 本地测试通过 / 真实依赖验证通过 / 云端部署验证通过 / 生产验收通过**。

## 0. 一页结论（TL;DR）

| 问题 | 结论 | 证据 |
| --- | --- | --- |
| 多副本 + 跨可用区部署是否真的成立 | **成立**：3 副本起、HPA 上限 9，且故障注入期间实测到 Pod 真的重排到别的可用区 | §2 副本分布、§5 第 2/3 项 |
| 单节点、单 Pod、控制面、**整个可用区**下线时服务是否还在 | **整区（az-b）下线只丢 3/40 个探针请求**（并发负载 0.01% 失败）；控制面 3→2 丢 4/32；删 1 个 api Pod 首次中断 12.9s、并发档失败率 72.3%（**与容量档同并发对照后才能归因，见 §5**）；删 PG 主库暴露了**两个应用侧缺陷**（§5.1） | §5 故障矩阵 |
| 依赖层（PG/Redis/MQ）是否自带复制与自动主从切换 | **是，但有明确边界**：CNPG 自动提升（首次中断 4.9s）；Redis Sentinel 提升时探针 0 失败；RabbitMQ quorum 探针 0 失败；**PG 挂掉 2/3 时 CNPG 把唯一存活实例提升为主库，写入并没有不可用**（预设被实测推翻，§5.3） | §4 依赖层自愈、§5.3 |
| 弹性伸缩是否按指标发生、代价多少 | **发生**：CPU 302% → HPA 3→9 副本，撤压后自动缩回；代价与拐点见 §6 | §6 弹性时间序列 |
| 容量与瓶颈在哪 | **三段实测，逐段定位**：①基线 `f96e49c` 固定 3 副本 `state@50` **成功 QPS 18.7**（本档唯一干净读数）；`state@100/200` 的 613/932 QPS 是假的 —— 97%–98.5% 的请求在入口被 502 挡下（应用分别只收到 277 / **12** 个请求）。瓶颈是应用自身：每请求 **60.5 条 SQL**、状态装配 p50 **1414ms**、纯读还付 **766ms** 写事务，而 PG 本身 p50 仅 **3ms**。②修完读路径（`4ca9658`）同入口同口径 **594.1 成功 QPS（+32×，错误率 0%）**、缓存命中 **40527/40527**；此时**瓶颈转到入口**：应用只吃 0.24–0.38/3 核、在途 ≤24、服务端 p50 8.4ms 平，**绕开 nginx LB 直打 NodePort 即 920.5 QPS（+55%）**，而压测机 node-03 整机 CPU 仍 **99%**。③把入口从「压测机上单容器」改成**集群内 3 副本跨 3 区**（NodePort 30081、上游 ClusterIP、PDB）后同口径 **1018.1 成功 QPS（1.73×）**、并发 50 的客户端 p50 **65 → 27 ms**；再叠加正文投影 **1042.3**，`state-all` 由投影从 59.7 抬到 **298.4（5.0×）**。**1018 / 1042 仍是下界**（压测源与 Prometheus 同机、单 JVM；§7.5） | §7 容量档、§7.4 天花板定位、§7.5 入口层对照、§8 逐模块归因 |
| 入口层是否单点 | **不再是**：入口从「压测机 node-03 上的单容器 nginx」改成集群内 **3 副本跨 3 可用区**（`topologySpreadConstraints` 强制打散 + `PodDisruptionBudget minAvailable: 2` + NodePort 30081 + 上游走 `daylight-api` ClusterIP）。负载下删 1 个入口副本：业务探针 **0/222 失败**、并发负载 **0/144789 失败**（QPS 1114.7、p95 123ms）、入口侧 `/lb-health` 故障期间**全程 200**、新副本 **2.1 s** 就绪。公网入口（node-07）已改指入口层，并去掉「把应用的 503 背压当上游故障重试」那条配置 | §7.5 入口层对照、`EDGE-CUTOVER.md`（改前/改后配置与复验） |
| 与 compose 档相比 | （待填，**不宣称谁更快**） | §9 |

**一句话边界**：本档验证的是「7 台 / 3 个真实可用区」这一范围内的真实分布式行为；
它不是生产验收 —— MinIO 单实例非 HA、持久卷是节点本地盘、**公网仍只有 HTTP（无域名/证书）**、
公网只有 5 Mbps、且**验证吞吐的容量档一律走内网 NodePort**（详见 §10）。
入口层本轮已从「压测机上的单容器」改成「集群内 3 副本跨 3 区」（§7.5），
但**这次改造是给比赛验收用的最小可用形态**，不是生产入口（没有 WAF、没有 HTTPS 终结、没有限流）。

## 1. 目标与方法学

### 1.1 要回答的问题（不是「跑个分」）

1. 把依赖层与应用层都换成自带复制/选主的组件后，**故障面**是否真的变小了：
   单 Pod、单节点、控制面 1/3、**整个可用区**分别下线时，用户看到什么？
2. **跨 AZ 是结构性保证还是碰巧**：副本/依赖实例的分布是否被强制打散，而不是概率事件？
3. 弹性伸缩在真实指标（CPU）驱动下是否发生，扩容的收益与代价各是多少？
4. 容量上限由**哪个模块**决定（逐模块归因），而不是给一个笼统的 QPS。

### 1.2 判定口径（可复算，不靠形容词）

- **QPS** = 样本数 ÷（首个样本开始 → 末个样本结束）的墙钟秒数；分位数取 nearest-rank。
- **成功 QPS** = QPS × (1 − 错误率)；错误率以 JMeter `.jtl` 的 `success` 列为准。
- **故障期错误窗口** = 探针侧「第一个非 2xx」到「最后一个非 2xx」之间的墙钟长度（**不是**注入到恢复的时长）。
- **ready 掉线** = `/health/ready` 返回非 200 的时长。
- 所有原始产物（JMeter `.jtl`、探针 CSV、HPA 时间序列、组件面证据）都留在结果目录里，报告只做解析与并排，不重新"美化"数字。

### 1.3 与生产环境的已知偏差（必须明说）

| 偏差 | 影响 | 为什么不修 |
| --- | --- | --- |
| 压测令牌是后端密钥**自签** JWT，不带 `jti` | 少一次会话行更新；其余鉴权路径（查库、会话版本校验）都被真实覆盖 | 登录接口强制图形验证码，无法脚本化；与 compose 档同口径 |
| 入口是压测机（node-03）上的 **nginx**，不是云 SLB/Ingress | 入口本身是单点（但挂了会立刻暴露，见 §5） | 客观条件；报告如实标注 |
| 明文 HTTP，无域名/证书 | 无 TLS 开销 | 未验证项，见 §10 |
| 公网 5 Mbps，全部负载走**私网** | 压测流量与业务流量不走同一条公网链路 | 规避公网瓶颈，两档一致 |
| 对象存储 MinIO 单实例 | 附件路径**不具 HA**（唯一非 HA 组件） | 7 台机器凑不出纠删码盘组，见 §10 |

## 2. 拓扑、参数与副本分布

### 2.1 集群拓扑（7 台 / 3 个真实可用区）

| 节点 | 公网 IP | 私网 IP | 真实可用区 | `daylight.dev/zone` | 角色 |
| --- | --- | --- | --- | --- | --- |
| node-01 | 192.0.2.10 | 172.31.122.146 | cn-hangzhou-i | az-i | **server**（嵌入式 etcd）+ 监控栈 |
| node-02 | 192.0.2.11 | 172.31.122.147 | cn-hangzhou-i | az-i | agent |
| node-03 | 192.0.2.12 | 172.31.122.148 | cn-hangzhou-i | az-i | agent + **压测/入口**（`daylight.dev/loadgen=true`） |
| node-04 | 192.0.2.13 | 172.31.38.169 | cn-hangzhou-b | az-b | **server**（嵌入式 etcd） |
| node-05 | 192.0.2.14 | 172.31.38.168 | cn-hangzhou-b | az-b | agent |
| node-06 | 192.0.2.15 | 172.28.226.210 | cn-hangzhou-j | az-j | **server**（嵌入式 etcd） |
| node-07 | 192.0.2.16 | 172.28.226.209 | cn-hangzhou-j | az-j | agent |

- 规格：4 vCPU / 7.5 GiB / 同一 VPC / 同一安全组（组内互通）/ 公网 5 Mbps。
- 控制面：3 个 server 各在一个可用区，`--cluster-init` 起嵌入式 etcd（3 个成员即多数派）。
- `daylight.dev/zone` 与**真实可用区一一对应**，因此"打掉一个区"就是真的打掉一个机房。
- CNI：flannel **vxlan**（跨子网必须封装；host-gw 的下一跳跨网段无法按 ARP 解析，见 §11.4）。
- 存储：`local-path`（节点本地盘；**卷不跨节点漂移**，这一点在 §10 如实记为边界）。

### 2.2 依赖层（自带复制与选主，应用零改动）

| 组件 | 形态 | 副本数 | 故障行为 | 跨 AZ 打散 |
| --- | --- | --- | --- | --- |
| PostgreSQL | CloudNativePG `Cluster` | 3（1 主 2 备） | 主库挂 → 自动提升备库，`daylight-pg-rw` 端点自动改指新主 | **强制**（`podAntiAffinityType: required`, `topologyKey: daylight.dev/zone`） |
| Redis | 官方镜像 3 节点 + 3 Sentinel + 2 HAProxy | 3+3+2 | 主库挂 → Sentinel 提升，HAProxy 改道到新主 | 强制（zone `DoNotSchedule`） |
| RabbitMQ | 官方镜像 3 节点 + **quorum 队列** | 3 | 挂 1 个节点队列仍可读写（2/3 多数派） | 强制（zone `DoNotSchedule`） |
| MinIO | 单实例 | 1 | **不具 HA**（明确标注） | 不适用 |

应用只换三个地址（`DAYLIGHT_DATABASE_URL` / `DAYLIGHT_REDIS_URL` / `DAYLIGHT_AMQP_URL`），业务代码不改一行。

### 2.3 应用层与编排策略

| 工作负载 | 副本 | HPA | PDB | 打散 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `daylight-api` | 3（HPA 3→9） | CPU 60% | `minAvailable: 2` | **zone 强制** + 节点尽量 | 滚动升级 `maxUnavailable: 0 / maxSurge: 1` |

| 入口 | — | — | — | 每区一个入口节点 | nginx `:8080` → 三区各一个 `NodePort 30080` |

- 驱逐容忍：`not-ready/unreachable` 各 60s（等节点判死后才重排）。
- 命名空间配额（按 7 台重算）：requests 20 CPU / 32Gi，limits 60 CPU / 72Gi，PVC 20，pods 64。
- 全部工作负载 `DoesNotExist: daylight.dev/loadgen` —— 压测/入口节点不跑业务副本。

## 4. 依赖层：自带复制与自动主从切换（实测）

三组依赖都由组件自身完成复制与选主，应用只改三个连接串（§2.2）。下面每一条都能在对应故障目录的
`component-inject.txt` / `component-after.txt` 里找到原文。

### 4.1 PostgreSQL（CloudNativePG，1 主 2 备，跨 3 区强制打散）

- 注入前：`INSTANCES 3 / READY 3`；删掉主库 Pod（`daylight-pg-1`）后立即快照：`READY 2`；
- 恢复后：`INSTANCES 3 / READY 3`，**`PRIMARY` 已从 `daylight-pg-1` 变成 `daylight-pg-2`**（提升确实发生了）；
- 业务侧：探针首个错误到首个恢复 2xx 之间隔 **4.9s**，`daylight-pg-rw` 端点自动改指新主；
- **但**探针错误跨度是 **197.2s**、并发负载失败率 **82.71%**（其中 502 有 10521 个）——
  放大这次故障的不是 PG，而是应用（§5.1 的两个缺陷）。

### 4.2 Redis（3 数据节点 + 3 Sentinel + 2 HAProxy，各组分属不同区）

- 注入对象是 **Sentinel 报告的当前主库**：日志原文 `pod "daylight-redis-0" deleted`；
- 恢复后 Sentinel 视角的主库是 `10.42.7.13`（`daylight-redis-2`，node-07）→ **主库身份确实切换了**；
  3 个 Sentinel 全程 Running；
- 业务侧：**探针 51 次请求 0 失败**（错误码分布为空），`ready` 掉线 0.9s ——
  说明 HAProxy 把连接改道到新主，抖动被代理层吸收，没有传到业务路径。

### 4.3 RabbitMQ（3 节点 + quorum 队列）

- 注入对象：`daylight-rabbitmq-2`；恢复后它重新 Running（新 IP `10.42.3.18`），
  而 `rabbitmq-0` / `rabbitmq-1` **全程没有重启**（uptime 连号）→ 任何时刻都有 2/3 存活；
- 业务侧：**探针 193 次请求 0 失败**，`ready` 未掉线。
- **口径提示**：探针只打 `/api/state`（读路径），不经过队列；所以这一项证明的是
  "节点挂掉时业务读路径不受影响"，**不是**"队列消息没丢"。消息不丢需要单独做投递-消费计数（未做）。

### 4.4 MinIO（单实例，**明确的非 HA**）

- `daylight-minio-0` 是**单实例**，删掉就是整体不可用；本轮只验证了"删它不会连带打挂读路径"
  （探针 174 次 0 失败），**附件下载/上传在这段时间不可用没有被测**（探针不经过附件路径）。
- 升级路径（未做）：MinIO 分布式纠删码，或改用云对象存储。7 台机器凑不出纠删码盘组，见 §10。

### 4.5 被实测推翻的预设：删 PG 主库 + 1 备库

原预期是"多数派不足 → 写入不可用"。实测：CNPG 把唯一存活的 `daylight-pg-3` 提升成了主库
（`INSTANCES 3 / READY 3 / PRIMARY daylight-pg-3`，另两个实例随后重建并追平），写入**并没有**不可用；
探针只有 10 次 500（错误跨度 163.7s）。异步复制下存活实例持有最新数据，
**"多数派丢失"不等于"写入不可用"**，真正的物理边界是"实例全没了"。这一条以实测为准（§5.3）。

## 5. 故障矩阵（9 项，含整个可用区下线）

> 逐项汇总表由 `fault-summary.mjs` 从原始 `probe.csv` + `analysis.txt` 生成，见 `FAULTS-baseline.md`（优化后见 `FAULTS-optimized.md`，对照见 `FAULTS-COMPARE-baseline-optimized.md`）。
> **另有 3 项复验**（同 3 类注入、修完的镜像 `4ca9658`、当时 9 副本）：见 `FAULTS-4ca9658-t3.md` 与 §5.4。

**先看口径**：探针是 1 req/250ms 的串行业务可用性；并发负载是 50 线程。
两个数差得多是正常的，**只报小的那个就是挑好看的报**。

| # | 注入 | 期望 | 探针 失败/错误跨度（首次中断） | ready 掉线 | 并发负载 失败率 / p95 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 删 1 个 api Pod | 用户无感 | 12/30（40%），跨度 55.2s（首次 12.9s） | 21.8s | 72.3% / p95 4885ms | 端点摘除生效，但**并发档失败率高**（与容量档同并发对照后才好归因） |
| 2 | 停 1 个 agent 节点 | 2/3 仍服务、Pod 重排 | 3/32（9.4%），跨度 33.6s | 10.7s | 0.97% / 5824ms | Pod 重排成功，短暂连接失败（`000`） |

### 5.1 本轮测量暴露的两个**应用侧**真实缺陷（依赖层没错，是应用没错住）

两项都来自第 5 项（删 PG 主库）。依赖层（CNPG 1 主 2 备）按预期完成了自动提升；
问题是应用侧把一次秒级抖动放大成了整体不可用：

1. **启动路径遇到依赖抖动直接退出**：9 个 api 副本全部 `reason=Error / exitCode=1`，
   崩栈是 `bootInfra → initPostgres` 的 `ECONNREFUSED`。副本同时重启 → 端点被摘空 →
   入口对所有请求回 502（该项负载 13475 样本失败 11145，其中 **502 有 10521 个**）。
   发现与证据：`FINDING-app-boot-crash.md`；修复已提交在 `feat/perf-and-observability`（`84444d3`），
   云端复验见 §5.4：同一项在有负载下失败率 **72.3% → 0.74%**，不再出现「全体副本同时重启」的形态。
2. **就绪探针做数据库往返**：`/health/ready` 每次 `SELECT 1 FROM daylight_jobs`，
   应用内部超时 5s 而 kubelet 探针超时 3s（必然不对齐）。故障窗口内实测
   **498 次** `Readiness probe failed: … context deadline exceeded`；
   **并已用对照实验确认**：无故障的弹性伸缩档（state=100，9 副本各 ≈1 核）期间同样出现
   （18:20 一分钟 64 次，原始证据 `elasticity/readiness-events-during-load.txt`）。
   机制与影响：`FINDING-readiness-probe.md`。修法与判据见 §11 缺陷 18/19/20；
   **云端修前/修后见 §5.4**（同一项负载失败率 72.3% → 0.74%，节点/整区故障期间探针 0 失败）。

### 5.2 这张表**测不到**什么（不许外推）

- **探针只覆盖 `/api/state`**，不经过附件路径 —— 所以第 8 项 MinIO 显示"无错"，
  这是**测不到**，不是"没影响"。MinIO 是单实例（明确的单点）。
- **整区下线只覆盖 az-b**。az-i（PG 主库 + 入口 LB + 压测机）整区下线的结果是
  「连不上测量工具」，测不出「系统怎么反应」，因此**未验证**，不能外推成"任意区挂了都没事"。
- 第 1 项的 72.3% 是**并发档**的数字，与探针的 40% 不是一回事，两者都要给。

### 5.3 被实测推翻的预设（写下来是为了不改口径）

第 9 项原本的预期是"挂掉多数派 → 写入不可用"。实测：CNPG 把唯一存活实例
`daylight-pg-3` 提升成了主库（`INSTANCES 3 READY 3 PRIMARY daylight-pg-3`），
写入并未因此不可用；探针只有 10 次 500（跨度 163.7s）。
**结论：异步复制下存活实例持有最新数据，多数派丢失 ≠ 写入不可用；
真正的物理边界是"实例全没了"。** 预设写法保留在汇总脚本里，便于对照。

## 6. 弹性伸缩

### 6.1 结论与状态（先说清楚）

- **HPA 本身按 CPU 正常工作**：3 → 6（+59s）→ 9（+90s），撤压后回落；集群侧复核当前为 `3/3`。
- **本阶段被标记为「阶段失败」，原因是脚本 bug，不是集群异常**：`elasticity.sh` 的参数行写成
  `WINDOW="…"# 注释`（引号后少一个空格），bash 不把 `#` 当注释 → 该行被解析成"执行一个叫
  `前/后对比窗口（秒）` 的命令" → 赋值被丢弃 → 后面在 `set -u` 下引用时报 `WINDOW: unbound variable`。
  **已修**（加空格），并全库扫过没有同类写法。窗口统计没跑成，本节用保存下来的 JTL 事后补算（`window-stats.mjs`）。
- **弹性伸缩只测了基线侧**：优化后每请求 CPU 下降，同样负载理论上需要更少副本，但**未测**，不宣称。

### 6.2 时间线（`hpa-timeseries.csv`，实测）

| 相对时间 | 副本（当前/期望） | CPU 利用率 | 就绪 |
| --- | --- | --- | --- |
| +0s | 3/3 | 2% | 3 |
| +59s | 6/6 | 302% | 3 |
| +90s | **9/9**（到上限） | 287% | 6 |
| +765s（撤压后） | 4/4 | 1% | 4 |

- 采样到的最大 CPU 利用率 **312%**（相对 request）；
- 单 Pod 资源（`top-timeseries.csv`）：CPU 峰值 **1290m**、p95 1027m；内存峰值 **922Mi**、p95 703Mi
  —— 9 个副本时 API 层合计约 **9–11 核**；
- 采样期间同一时刻的 api 副本数：3 → **9**（与 HPA 时间线一致）。

### 6.3 这一档暴露的**最严重**问题：扩容之前业务大面积不可用

同一批 JMeter 样本按窗口切开（`window-stats.mjs`，窗口 120s）：

| 窗口 | 样本数 | QPS | **成功 QPS** | 错误率 | 错误码分布 | p50 |
| --- | --- | --- | --- | --- | --- | --- |
| 全程 | 49857 | 82.7 | **31.4** | **61.99%** | 502×30851、200×18952、503×54 | 10ms |
| 前 120s（副本数还没上来） | 33964 | 270.5 | **24.4** | **90.98%** | 502×30851、200×3062、503×51 | 5ms |
| 后 120s（已扩到 9 副本） | 3986 | 31.6 | **31.6** | 0.05% | 200×3984、503×2 | 2956ms |

**读法（很重要）**：

1. 前 120s 的 QPS 270 是**假的**：30851 个 502 全部集中在这 120s，502 由入口在
   *没有可用上游* 时立刻返回（约 24ms），把"失败很快"算成了"吞吐很高"；
   **所以只报 QPS 会把一次大面积不可用说成一次性能提升**，必须看成功 QPS（24.4）。
2. 502 的来源已经查清，不是网络问题：3 个副本在 100 并发下各自打满 **≈1 核 CPU 上限**
   → `/health/ready` 的数据库往返来不及 → kubelet 3s 超时 → 连续 3 次失败 → Pod 被标记不就绪
   → 端点被摘空 → 入口对所有请求回 502。事件侧实测到 498 次
   `Readiness probe failed: … context deadline exceeded`（含**无故障**高压期的 18:18–18:21，见
   `FINDING-readiness-probe.md` 与 `elasticity/readiness-events-during-load.txt`）。
3. 扩到 9 副本后错误率降到 0.05%，但**成功 QPS 只有 31.6**：说明基线代码（75 SQL/请求）
   在云端 vCPU 上的单请求成本很高，p50 仍 2956ms。这正是存储读路径优化要解决的问题——
   优化后的对照见 §7。

### 6.4 代价

- 扩到 9 副本的代价：API 层 3 → 9 个 Pod（每 Pod 峰值 1.29 核 / 922Mi），
  即约 **+6 核 / +4 GiB** 的瞬时资源；HPA 上限 9 是当前的硬顶（再高的负载只能是排队）。
- 缩容：撤压后 CPU 降到 1%，副本回落（本档采样窗口内到 4，集群侧复核最终 `3/3`）。

## 7. 容量档

### 7.1 本节口径（先说清楚，再看数）

- **固定 3 副本**测的：测量前把 `daylight-api` 的 HPA `min=max=3`（否则量到的是"带自动扩缩的容量"），
  测完还原成 `min=3/max=9`（实测还原成功）；`worker` 不动。
- 与弹性档是**两件事**：弹性档回答"会不会按指标扩"，本节回答"固定副本下能扛多少"。
- 场景与基线完全一致：`state=50,100,200` + `state-all=100`，每档 30s、爬坡 5s，入口是压测机上的容器 LB。
- **一律报「成功 QPS」**（= QPS × (1 − 错误率)）：失败请求会立刻返回（实测约 24ms），
  只报 QPS 会把"大面积不可用"写成"吞吐很高"。本档 `state@100` 就是这种陷阱的教科书案例。
- 令牌坑（工具链缺陷，已记入 §11）：容量档读的令牌路径与结果根不一致，第一次跑整段失败；
  补齐令牌后重跑，`k8s-r1/` 才是有效数据。

### 7.2 结果（基线 `f96e49c`，固定 3 副本，2026-10-17 18:42–18:54Z）

| 场景 | 并发 | 样本 | QPS（含失败） | **成功 QPS** | p50 | p95 | 错误率 | 主要错误码 | 平均响应体 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `state` | 50 | 589 | 18.7 | **18.7** | 1995ms | 5165ms | 0.00% | — | 171 KiB |
| `state` | 100 | 18965 | 613.5 | **17.9** | 6ms | 41ms | 97.08% | 502×18361、503×51 | 5.3 KiB |
| `state` | 200 | 34852 | 932.5 | **14.0** | 4ms | 39ms | 98.50% | 502×33959、503×370 | 2.9 KiB |

| 场景 | 客户端发出 | 应用实际收到 | 说明 |

`state@50` 那一档是本档唯一"干净"的读数：3 个副本、18.7 成功 QPS、p50 1995ms、

### 7.3 怎么读（三条必须一起读）

1. **`state@100/200` 的成功 QPS 会被应用侧缺陷压住**，不是机器到顶：3 个副本在 100 并发下各自打满
   ≈1 核 CPU 上限 → `/health/ready` 的数据库往返超时 → 端点被摘空 → 入口对每个请求立即 502
   （该档失败样本里 502 占绝大多数）。同形态已在弹性档确认（§6.3）。
2. 因此**容量上限的结论只能是"在当前镜像与当前缺陷下"**：修掉就绪探测、并按本轮存储读路径优化
   降低单请求成本之后，同一档位的成功 QPS 会显著不同（对照见 §7.4）。
3. 低并发档（`state@50`）没有触发摘除，它的成功 QPS 更接近"这台机器真实能做的吞吐"，
   可作为"单请求成本"的干净读数。

| `state@100` **直打 NodePort（绕开 LB）** | **920.5** | 63 ms | 64% / **99%** | 0% | 234–387% | 88 MB/s（峰 273 MB/s = 2.2 Gbps） |

三条结论，都可复算：

1. **上限随响应体字节数走，不随并发走**：把 5 个点拟合，每请求固定成本 ≈ **0.49 ms**
   （对应 `health` 的 ~2050 QPS），**每 MB 响应体 ≈ 6.9 ms（≈145 MB/s）**。`state` 的 175 KB × 589 = **824 Mbps**，
   要从 node-03 过两遍（LB 容器 + JMeter），而 node-03 只有 **4 核 / 7 GB**，上面同时住着 JMeter、nginx LB 和 Prometheus。
2. **nginx LB 容器本身就是吞吐瓶颈**：只改入口（绕开 LB 直打 `node02:30080`）就 **+55%（594 → 920）**，
   而它的 CPU 峰值 **230%（2.3 核）**。这不是测量误差 —— 单点 LB 跑在共享节点上，**既是 SPOF 也是吞吐上限**，
   这条实测正好是企业级拓扑（P2 ingress 分层）的动机。
3. **去掉 LB 后 node-03 仍钉在 99%**，剩余上限是**压测源自己**（单 JMeter JVM 峰值吃满 4.0 核）。
   所以本轮**测不到系统天花板**，只能给下界。

**顺带纠正一条旧说法**：`state-all@100` 的 52 QPS 也**不是**应用「拼不出响应」——
同一档应用侧 CPU 只有 **1.8%**（峰值 9.3%），而它的响应体是 3.34 MB，
52 × 3.34 MB = **175 MB/s**，同样落在上面那条「每 MB ≈ 6.9 ms」的字节预算里。
即：本轮 `state` 与 `state-all` 两个数字**都是被测量链路压出来的下界**，
不能用来判断 `scope=all` 到底能不能优化 —— 要判它必须先把响应体降下来（投影/分页）再测。

**因此本轮容量的口径只有一句话**：`≥ 920 成功 QPS @3 副本（直连 NodePort，错误 0%）`；
与基线可横向比较的是**同入口**的 `594.1`（+32×）。两个数字都必须带入口说明，否则不可比。

新增三条缺陷记在 §11（20 校验池未采埋点、21 压测源与被测链路共用节点）。

## 8. 逐模块瓶颈归因

数据来源：应用自己的埋点（每个副本各一个 JSONL，`breakdown.mjs` 汇总；原始输出留在
`k8s-r1/BREAKDOWN-baseline.txt`）。**先看归因，再谈结论** —— 这一节回答"慢在哪一层"。

### 8.1 每请求的数据库代价（回答"列表接口装了不该装的"）

| 量 | 实测（基线） | 怎么算的 |
| --- | --- | --- |
| `2xx` 的 `/api/state` 请求数 | 8956 | 埋点里 `http.request.ms{route=/api/state,status=200}` 的计数 |
| `select` 总数 | 441728 | `pg.query.ms{op=select}` |
| **每请求 `select`** | **49.3 条** | 441728 ÷ 8956 |
| 每请求 `commit` / `begin` | 5.6 / 5.6 条 | 同上 |
| **每请求 SQL 合计** | **约 60.5 条** | select+commit+begin |

一条只读的状态查询要打 **60 条 SQL**，这是"单邮箱视图却把所有邮箱的数据都读进来"的直接证据。

### 8.2 时间花在哪（分位）

| 指标 | 次数 | p50 | p95 | max | 均值 |
| --- | --- | --- | --- | --- | --- |
| `storage.snapshot.ms`（装配状态快照） | 12523 | **1414ms** | 3770ms | 6813ms | **1575ms** |
| `storage.commit.ms{docs=0}`（**纯读**付的写事务） | 8973 | 766ms | 2132ms | 4054ms | **895ms** |
| `http.request.ms{/api/state, 200}`（端到端） | 8956 | 2897ms | 5703ms | 8699ms | 2949ms |
| `pg.query.ms{op=select}`（数据库本身） | 441726 | **3.06ms** | 151ms | 4281ms | 49.5ms |
| `pg.query.ms{op=commit}` | 49950 | 2.9ms | 114ms | 1758ms | 24.7ms |

**结论**：数据库 p50 只要 **3ms**，端到端 p50 却是 **2897ms** —— 慢的不是 PG，是应用把整份
状态**重复装配**（1.4s）并**为只读请求提交写事务**（766ms~895ms）。尾部分（`select` p95 151ms、
max 4.3s）与连接池竞争（`pg.pool.waiting` p95 4、max 39，池上限 8）有关，但量级远小于前两者。

### 8.3 资源与事件循环

| 指标 | p50 | p95 | max |
| --- | --- | --- | --- |
| `process.rss.bytes` | 206 MiB | 526 MiB | **969 MiB** |
| `process.heap_used.bytes` | 49 MiB | 258 MiB | **746 MiB** |
| `eventloop.delay.ms{stat=max}` | 29ms | 296ms | **980ms** |
| `http.inflight` | 8 | 21 | 44 |

峰值 RSS 接近 **1 GiB**（与 §1.1 的观察一致），事件循环有近 **1s** 的停顿 —— 这两项都是
"单进程既装配又序列化整份状态"的直接后果，而不是数据库或网络的问题。副本的 CPU 上限是 1 核
（弹性档实测单 Pod 峰值 1290m），所以高并发下先撞的是应用自身的算力，而不是后端。

## 10. 局限与未验证项（不美化）

1. **MinIO 单实例**：附件路径不具 HA，故障矩阵第 8 项会**失败**，这是如实记录而不是通过。
2. **`local-path` 本地盘**：PG 的卷绑定在首次调度的节点上；该节点彻底死掉时，实例会在同区另一节点上重建，但**旧卷不会漂移**（数据来自副本同步）。生产应换复制型存储（Longhorn/Ceph 列为可选，未启用）。
3. **依赖层的多数派是 3**：同时丢 2/3 写入不可用（第 9 项），这是 3 副本的物理边界，不是 bug。
4. **入口是压测机上的 nginx**：不是云 SLB；它所在的节点故障会让入口一起消失（本档把它放在 az-i 并只做 node-kill，不参与整区下线）。
5. **公网 HTTPS / 域名 / 证书未验证**（当前为明文 HTTP）。
6. **真校园邮箱不可达**：Coremail 反垃圾拒收校园语料邮件，本地校园 IMAP 不可靠 → 真实收发链路的云端验证仍缺。
7. 只有一个可用区做过整区下线（az-b）；az-j 作为补充用例（§3 命令），结果同样如实记录。
   **az-i 没测、也测不了**：PG 主库、控制面节点、入口 LB 与压测机都在 az-i，把整区打掉会连带毁掉测量链路本身，
   得到的是「连不上」而不是「系统怎么反应」。所以「整区挂了仍服务」这句话在本档**只对 az-b 成立**，
   对 az-i（主库所在区）是**未验证**，不能外推。
8. 「7 台 / 3 AZ」之外的分区容灾（跨 region、跨 VPC）**未验证**。
9. **NodePort 对公网暴露**：实测 `http://<任意节点公网 IP>:30080/health/ready` 全部返回 200，
   也就是 7 台机器各有 1 份应用入口。控制台侧的安全组没有权限改，已作为待办交付
   （`work/enterprise-acceptance/P4-nodeport.md`，含集群侧收口脚本）。这属于**网络面未收口**，不是已完成项。
10. **依赖层没有退到「数据节点单机」形态**：冻结稿把 PG/Redis/MQ 放在 test-01，
    本次按用户决策保留跨可用区多副本（否则 az-i 一挂业务全停，与第 7 条的结论矛盾）。
    这是与冻结稿的**唯一形态差异**，取舍理由见 `work/enterprise-acceptance/RUNBOOK.md`。
11. **控制面节点是 node-01/04/06，不是冻结稿写的 02/04/06**：两者都跨 3 个可用区，可用区级容灾性质等价；
    重排需要卸载/重装 k3s（会打掉 node-02 上的 PG 主库），在没有额外容灾收益的前提下只增加风险，故未做。
12. **本轮容量数字是下界，不是系统天花板**（缺陷 21）：压测机 node-03 同时住着 JMeter、nginx LB 和 Prometheus，
    只有 4 核；`state@100` 走 LB 得 594 QPS 时该机整机 CPU 已 **99%**（JMeter 单进程峰值 4.0 核），
    绕开 LB 直打 NodePort 拿到 **920 QPS** 时仍是 **99%**。因此只能写成
    「**≥ 920 成功 QPS @3 副本（直连入口）；同入口同口径 ≥ 594**」，
    **不得**表述成「系统上限 594 / 920 QPS」（§7.4）。
13. **响应体大小本身未优化**：`/api/state` 175 KB、`scope=all` 3.3 MB 是绝对吞吐的真实相关量
    （拟合出每 MB ≈ 6.9 ms）。投影/分页/流式属于接口层重构，本轮未做，也不假装做了。
14. **校验查询的成本尚未采到埋点**（缺陷 20）：`pg.query.ms` 只覆盖业务池，校验池漏了 `instrumentPool()`；
    所以「命中 = 一条小 SQL」目前只有代码依据、没有线上计数。修它要给池指标加前缀，避免污染 `pg.pool.*`。

## 11. 本轮修掉的真实缺陷（都是"看起来在跑，其实没跑通"那类）

| # | 缺陷 | 症状 | 根因 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | 远端 `nohup … &` 继承 ssh 的 fd | 分发脚本**永不返回**，ssh 挂死 | 后台进程持有 stdout/stderr，ssh 等 EOF | 拆成两次 ssh；`setsid` + `</dev/null >/dev/null 2>&1`；`pgrep` 落 pid |
| 2 | `while read … < 文件` 循环体里调 ssh | 清单只处理**第一台**节点 | ssh 把循环的 stdin 吃光 | 改 fd 3：`read … <&3` / `done 3<"$NODEFILE"` |
| 3 | k3s containerd 没有 registry mirror | 所有 Pod 卡在 `CreatePodSandbox`（集群一个 Pod 都起不来） | 节点直连 docker.io 拉 `rancher/mirrored-pause` 超时 | 写 `/etc/rancher/k3s/registries.yaml` + 重启 |
| 4 | flannel `host-gw` | 跨子网 Pod 网络 `Network is unreachable` | 下一跳需 ARP，跨网段解析不了 | 用默认 **vxlan** 封装 |
| 5 | LB 缺 `proxy_next_upstream` | 后端一个副本瞬断 → 502（实测触发过 502 风暴） | nginx 默认不重试，`max_fails` 把**所有**副本一起摘除后无可用上游 | `proxy_next_upstream error timeout; tries 3; timeout 5s` |
| 6 | LB 入口只取到 1 个区 | 入口冗余与"整区下线自动改道"是假的 | `zone_entry_targets()` 写死了 `az-a…az-e`，而真实 zone 是 `az-i/az-b/az-j` | 从节点清单里 `sort -u` 取 zone |
| 7 | `quiesce.sh` 静默"成功" | 以为 compose 栈停了，其实容器还在跑（会污染 k8s 档的资源/延迟判断） | 缺 `--env-file`、`DAYLIGHT_DEP_BIND` 取值错，`docker compose stop` 作用在空项目上返回 0 | 补参数 + stop 后**复验容器真的不在跑**才返回成功 |

## 12. 复现性与参数

- 参数快照：`results-k8s/PARAMS.md`（节点清单、版本、K8s 对象、配额、探针与压测参数、镜像与提交溯源）。
- 节点清单（脚本的单一事实来源）：`results-k8s/nodes.tsv`。
- 逐阶段日志：`results-k8s/logs/`。
- 原始结果：`results-k8s/{netcheck,faults,elasticity,k8s-r1,obs}/`。
- `tests`（脚本）与 `results`（原始数据）的对应关系：
  - `fault-summary.mjs` → `FAULTS-<label>.md/json`（逐项汇总，含"未验证"与逐项口径提示）
  - `fault-compare.mjs` → `FAULTS-COMPARE-<a>-<b>.md`（前后对照，故障项只比错误率与 p95）
  - `analyze-fault.mjs` → 每项 `faults/<name>/{analysis.txt,result.json}`（错误跨度与首次中断分开报）
  - `results-k8s/FINDING-*.md` → 本轮暴露的应用侧缺陷（含现场证据与"尚未验证"的边界）
- 报告里的每个数字都能从上述产物重算（`fault-summary.mjs`、`fault-compare.mjs`、`breakdown.mjs`、`cloudlab.sh summarize`）。

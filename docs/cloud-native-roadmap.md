# Daylight 云原生建设与比赛验收基线

更新日期：2026-10-16（北京时间）。本文件定义建设目标与交付标准；已实现功能、实测结果和缺口以 [STATUS.md](../STATUS.md) 为准，操作入口见 [README.md](../README.md)，部署说明见 [DEPLOY.md](../DEPLOY.md)。

## 1. 目标与场景价值

Daylight 的目标是完整、可落地、可运营的商业化云原生 Agent 系统，面向 UCloud 校招比赛赛道 B「AI Application（云原生智能体应用与场景创新）」。比赛依据为用户提供的题目截图，不额外推定指定云产品、评分权重或必须使用全部技术。

以统一工作区里的场景工作台组织现有邮箱、日历、待办、附件、检索和执行记录。账号不再按普通用户或 HR 限制功能。侧栏提供「我的工作台」与「管理工作台」（可添加、移除已有入口）。内置模板各自走确认后的闭环：智能招聘与发票助手标为官方模板，保研、申博、校招、投稿标为社区模板；外部发送仍要人工确认：

- 保研、申博/RA、校招、科研投稿：关联通知 → 按规则生成材料与行动，并只记录建议阶段 → 用户采用阶段、确认写入待办或日历 → 用回执区分已准备、已提交和对方确认。已申请、已投递、申请中、已投稿、终稿/注册和正式结果这些阶段，没有回执不能进入。
- 智能招聘：复用原招聘引擎处理简历、筛选、邀约审核、发信和会议。工作台不复制候选人；简历邮件只生成待确认的筛选待办。`/app/recruitment` 仍直接打开原页面。
- 发票助手：复用原发票提取与字段复制。发票邮件生成待核对事项；提取结果需对照原件，不自动改日程或待办。可报销阶段需要回执。`/app/invoices` 仍直接打开原页面，也可以从发票工作台进入同一套页面。
- 个人日程：接收邀请及变更 → 提取安排与待办 → 检查冲突并提出方案 → 用户确认后回信/同步日历 → 追踪结果与后续变更。
- 上述闭环的本地规则和页面已有验证。真实 IMAP、模型和 SMTP 仍分开记录，未授权前不把本地样例写成真实联调。
- 小 D：起草邮件或飞书会议邀约后进入审核卡，用户确认才发送。草稿、请求和会议操作按邮箱持久化；PostgreSQL 启用后为权威，不可用时不退回旧文件。工作台保存的回复草稿不发信；放入小 D 审核后也要在审核卡确认才发送。

目标用户、痛点与收益需通过实际使用验证。记录人工处理耗时、遗漏或冲突数量、任务成功率与人工修正率，和未使用 Agent 的基线比较；不把“调用了模型”本身当作业务价值。商业化建设还需明确用户/组织边界、权限与数据生命周期、服务支持、配额及单位经济性；收费方案在用户与成本验证后确定，不在本轮预设付费功能。

## 3. 架构演进

当前 React + Node、`server/infra/*` 及已有业务模块是演进起点。保留便于复现的本地开发路径，不以单机、单进程或 JSON 存储作为架构上限。

1. **应用与任务解耦：** 区分前端/API、邮箱同步调度、模型/OCR 等后台 Worker；先建立清晰执行边界，再按负载独立部署。长任务不依赖某个 Web 进程存活。
2. **共享状态：** 生产以 PostgreSQL 保存权威业务与任务状态，对象存储保存附件；明确 Redis 的临时状态用途。逐项检查日历、招聘、配置、会话、日志和任务状态，不能只迁移部分数据就宣称无状态部署。落实事务、版本控制或唯一约束，验证跨实例幂等和邮箱顺序处理。场景工作台按用户存在 `scenarios:<用户ID>`（未开 PostgreSQL 时为 `scenarios/<摘要>.json`）。邮件与附件仍在原邮箱存储，工作台只保存引用；确认后的待办和日程写入原日历。同一行动只写一次；同一封邮件、同一待办标题，或同一封邮件的相同时刻，跨工作台也不再写第二条，这条记录会记下相关的每个工作台。带钟点的面试、面谈或报告在确认前只是待写入日程。工作台待办完成前要登记回执。待办勾选完成后只在工作台标出「待办已完成」，不改变已提交、已发送或对方确认。从日历删除工作台写入的安排后，行动记录保留并标出「日程已从日历删除」。改期保留已取消的原日程。按规则或模型生成的建议阶段只记在事项上，用户采用后才改看板。招聘工作台只读引用已关联邮件的招聘附件和执行记录，不复制候选人，也不在此发邀约。内嵌招聘和发票读取工作台绑定的邮箱，不改活动邮箱。该 PostgreSQL 路径尚未做真实数据库多实例验收，也尚未用真实邮箱、模型和发信验收。
3. **可靠执行：** 消息确认、失败重试、退避、死信/人工处理和重启恢复需有明确语义。针对 SMTP/日历等外部副作用处理“调用成功但本地保存失败”及超时未知状态，避免盲目重试导致重复发送；保留人工确认和可追溯补偿。
4. **容器与编排：** 提供应用/Worker 镜像、配置与密钥注入、健康检查、资源请求/限制、优雅停机及滚动发布/回滚。Kubernetes 按 CPU、队列积压等实测指标设计扩缩容；先验证共享状态及调度互斥，再增加副本。
5. **云服务选型：** 评估 UCloud 的数据库、缓存、对象存储、计算/容器及消息服务与现有协议的适配。当前 RabbitMQ 接入不能自动视为兼容其他 MQ；配置中出现供应商名称不等于已实现适配或实连。记录选型、协议、成本及验证结果。
6. **生产运维与安全：** 建立日志/指标/Trace 关联、告警、备份恢复、权限隔离、密钥保护、数据保留/删除及发布回滚。邮件与附件始终作为不可信输入；工具权限由服务端校验，不能执行邮件中的指令。

开发模式可使用本地回退。生产依赖不可用时，应根据业务选择暂停、拒绝写入或进入明确可恢复的降级状态，并告警；禁止把静默写入某实例 JSON、内存验证码或进程内队列当成高可用。上述策略是待实现和验证的目标，本轮文档调整未改变运行行为。

## 4. 建设阶段与完成条件

| 阶段 | 交付重点 | 完成条件 |
| --- | --- | --- |
| 业务闭环与基线 | 选定主展示场景，整理工具、状态和权限边界，建立代表性与异常样本集 | 核心端到端流程可复现，真实链路与模拟环节标注清楚，记录质量和人工修正基线 |
| 云端可部署 | 应用容器化、共享存储、任务解耦、配置/密钥管理、云依赖接入 | 从干净环境部署成功，核心业务使用真实云依赖运行，重启后数据和任务可恢复 |
| 多实例与运营保障 | Kubernetes、并发幂等、调度协调、伸缩、故障恢复与告警 | 多副本不重复执行业务副作用；依赖中断、Worker 重启、滚动发布及备份恢复有验证记录 |
| 比赛与商业化验收 | 架构文档、演示视频、可复现源码、质量与成本性能报告、运营边界 | 材料与实际版本一致，已完成/待完成明确，按声明负载满足约定的服务与成本目标 |

具体容量、SLO、恢复时间/数据恢复点及成本预算应在基线测量后确定，并在验收前固定；不得凭空给出已达标的数字。优先完成一条有价值的业务闭环，而不是同时引入与场景无关的基础设施。

## 5. 验证和证据管理

- 本地回归：按改动运行 `npm test`、`npm run build` 及必要交互检查；使用独立数据目录，不覆盖用户数据。
- 集成与云端：验证真实依赖、权限隔离、重复投递、多实例竞争、模型超时、外部调用失败及恢复；对真实发信和付费调用使用授权的测试账号与范围。
- 质量与性能：区分预置样例、合成输入调用真实模型、真实邮件端到端三类结果；分别测量冷启动/缓存、新邮件/去重及正常/故障负载，记录环境、样本量、模型配置、用量与费用来源。
- 交付报告：每条结论关联版本、日期、操作步骤、预期/实际结果及脱敏证据。`work/` 可保存临时材料；比赛交付需要的脱敏报告与可复现脚本应纳入仓库文档或随版本发布，不能只引用某台机器的临时文件。
- 状态分级：规划中、代码已实现、本地测试通过、真实服务实连成功、云端部署验证通过、生产验收通过分别记录。现有本地测试通过和历史真实联调不能替代后续云端验收。

## 2. 本轮新增证据

本轮新增结果在完成运行后登记于 [评测报告](evaluation-report.md) 和 [STATUS](../../STATUS.md)。评测入口与口径见 [评测说明](evaluation.md)。

- 合成邮件是人工编写的测试输入；真实模型调用与预置模型响应是两种不同证据。
- 提取评测调用基础邮件分析与内存应用，不连接 IMAP/SMTP，不覆盖工作台关联、浏览器、云部署或最终外部送达。
- 前置回执修复的合成回归证明“准备待办不等于完成前置”；人工登记回执仍不等于从外部系统自动验证事实。
- 全量回归与构建仅在实际运行通过后记录数量，保留失败与重跑记录。

## 3. 当前架构的关键核查结果

以下是对起始版本的代码审查，不是故障注入结果。下一次改造后应以新版本重验。

| 核查对象 | 现状 | 直接影响与验收任务 |
| --- | --- | --- |
| [应用入口](../../server/index.js)、[Compose](../../docker-compose.yml) | 同一进程承载 API、前端、调度与消费者；固定回环监听；Compose 只启动 RabbitMQ | 应用镜像、容器监听与探针尚需交付；不能仅凭 Compose 命令称全栈部署 |
| [普通邮箱存储](../../server/store.js) | 普通日历读本地 JSON、先写 JSON、异步写 PG；不同模块权威语义不一致 | 统一共享状态与失败策略后才能扩大副本；先列出全部写入路径和迁移对账 |
| [任务队列](../../server/infra/queue.js) | 进程内任务历史、普通发布 channel、失败不重投且没有完整死信恢复；连接失败可回本地 | 消息持久标志不等于端到端可靠；任务账本、确认、重试及外部副作用需一起验收 |
| [同步调度](../../server/index.js) | 自动任务缺少固定用户/邮箱身份，消费时读取当前设置；互斥主要在进程内 | 队列任务必须绑定 owner/mailbox；验证切换邮箱、重复调度、同邮箱并发和重启 |
| [场景计划](../../server/scenarios/service.js) | 模型分析与确定性规则共同生成建议；工作台分析的独立模型 trace 尚不完整 | Demo 逐步标明模型和规则；补工作台模型 usage/延迟/来源，不能展示基础邮件 trace 冒充工作台分析 trace |
| [场景计划](../../server/scenarios/service.js) | 历史作废通知的来源选择仍需复核；分析可能忽略作废后新增要求 | 补“旧通知→作废→新通知”的时间顺序及回执回归后再纳入主演示 |

基础日历路径不宜笼统写成“已实现 PG 唯一权威”。场景和小 D 已有局部事务、锁与未知状态保护，应分别说明覆盖范围。进一步的架构与取舍见 [云原生设计](../why_test/README.md)，其中目标拓扑与预算假设仍须和实际部署分开。

## 4. 最终发布必须登记

1. 提交 SHA/Tag、源码快照 SHA-256；如有未提交改动，不能只用 HEAD 标识已测代码。
2. 模型请求名、提供方、提示词/评测集哈希、配置白名单、价格口径及测试日期。
3. 原始逐例结果、失败与未知费用、样本量、统计口径、计时起止、CPU/RSS 归属进程。
4. 实际部署地域、机器规格、镜像 digest、持久卷/PG/对象存储实际用途；未启用组件不画成实线已部署服务。
5. 一次干净部署、一条真实业务链、一次重启/恢复或明确失败的记录；实际范围内保留可复现命令。
6. 5 分钟汇报、3 分钟实演、备用视频、访问方式和现场相对提交版的变更说明。

未完成项目继续写“待验证”。一等奖冲刺的重点是让评委逐条核验价值、执行结果和取舍；有限样本通过不等于生产可靠性或未来获奖承诺。

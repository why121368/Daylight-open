## 冻结顺序

1. 汇总并行修改，确认 API、Worker、Scheduler 入口与部署命令一致；审查所有权威状态路径和外部副作用语义。以最终代码更新 [架构](architecture.md)，不沿用过时的“仅 MQ Compose”说明。
2. 使用隔离数据运行影响范围内的单元/HTTP/共享存储/任务测试及前端构建。执行真实 PG/MQ 验证，归档命令和退出码。历史 STATUS 的数量不能作为新提交的通过数量。
3. 按 `deploy/README.md` 和 `DEPLOY.md` 完成干净环境迁移与启动，核验健康、停机、重启、权限隔离及数据持久。实际执行记录进入 `deploy/VALIDATION.md` 或独立证据包。
4. 完成 [可靠性矩阵](reliability/README.md) 与 [性能测量](performance/README.md) 中本次承诺的范围。未做项保持待验收；成本缺 usage 或账单时保持未知。
5. 在授权范围内运行真实通知→模型→确认→结果追踪，外部发信单独获得明确操作授权。示例、stub、真实服务日志分别标识来源。
6. 确定 SHA、镜像 digest、部署配置版本与数据 schema 版本；再更新截图、讲稿、视频和在线实例。录制完成前不填入“视频已生成”。

## 回滚与恢复验收

发布前保存当前镜像 digest、配置版本、PG 备份及对象清单。备份与恢复含个人数据，应保存在受控位置，公开材料仅放脱敏清单与校验结果。迁移必须先验证旧程序兼容性；不能假设回滚镜像会自动回滚 schema。

隔离环境中先停止新任务提交并等待或记录运行中任务，回滚到已验证镜像，确认健康与任务状态，再重放同键请求检查幂等。若数据库迁移不向后兼容，应按已演练的恢复方案恢复到独立环境并核对数据，然后决定切流。不要将删除卷、关闭 PG 或恢复旧 JSON 当作生产回滚方式。

目前回滚演练、备份恢复、RTO/RPO 均待测。部署清单里的重启策略、宽限时间和探针只是配置，不是恢复成功证据。

```text
manifest.json                 # SHA、dirty、版本、环境、起止时间、授权范围
checks/                       # 测试与构建命令、日志、退出码

reliability/                  # 注入点、任务 ID、预期/实际、失败记录
performance/<run-id>/         # raw.jsonl、summary.json、环境补充
business/                     # 脱敏来源、trace、确认与真实回执
presentation/                 # 实际生成后才加入幻灯片与视频
```

以上是目录约定，不是已存在的证据清单。公开包不能包含 API Key、授权码、SMTP 密码、完整连接字符串或私人邮件正文。提交前逐个链接检查文件真实存在，逐项核对宣称与原始证据一致。

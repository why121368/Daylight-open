# Daylight 路演讲稿（约 4 分 40 秒至 5 分钟）

## 第 1 页｜封面（15 秒，累计 0:15）

各位评委好，我是俞云烽。很高兴今天能向大家介绍我们这两天开发的项目——Daylight，一个邮件驱动的 Agent 工作台。我们想解决的问题很直接：收到了很多邮件，能不能更方便地管理和模糊检索？

## 第 2 页｜邮件太多（40 秒，累计 0:55）

这个想法其实从我入学开始就一直在酝酿了。上科大平时的通知都是以邮件的形式发送的，这就导致一个问题：就是各类活动比如讲座、产业报告、以及交材料等常常混在一起。有时看过就忘了，有时记得有这件事，却很难找到原来的邮件，比如最近秋招有很多宣讲会的邮件，我常常得自己在备忘录里记录一下，不然很容易错过，有时忘了又要回去翻邮件。同样的问题还可以延伸到很多以邮件为主要沟通的场合，比如招聘、发票、保研陶瓷等等。

所以，我们想做的，不只是一个邮件客户端，而是一个能帮用户找回邮件、整理日程和待办，并持续跟进后续变化的工作台。因此我们开发了 Daylight 这个项目。


## 第 3 页｜所以做了 Daylight

具体来说，我们把邮箱、日历和待办放在了一起，同时做了一个类似插件市场的工作台社区。用户可以根据自己的需要添加不同的工作台，比如智能招聘、发票助手，或者保研、申博、校招和投稿。后续也可以按统一的模板格式扩展新场景，复用已有的收信、附件处理和检索功能，不用每次都从头开发。

## 第 4 页｜查找与操作

比如我只记得之前收到过一封讲座通知，但忘了标题，也不记得是谁发的，就可以直接问：“之前那场讲座是什么时候？”我们结合了关键词和向量检索，不需要用户准确记住原来的措辞。回答里也会带上原邮件，方便点进去查看。除了找信息，系统还可以整理日程、待办，或者准备回复草稿。工作台里的建议要先确认再写入，发信也需要审核；基础邮件同步则会按提取结果生成日程和待办。

## 第 5 页｜系统架构

Daylight 整体采用分层架构，并将交互请求与耗时任务分开处理。

最上层是 Web、Desktop 和 iOS 客户端，通过统一的 HTTP API 和 SSE 接入后端，共用账号、业务数据和任务状态。接入层统一完成身份认证、权限校验和邮箱范围检查，保证多用户、多邮箱之间的数据隔离。

业务层围绕邮件、日历和待办提供通用功能，上面承载智能招聘、发票助手等场景工作台。场景之间复用邮件处理、材料管理和检索能力，通过模板配置表达不同的业务流程，降低后续扩展的开发成本。

Agent 层负责结构化提取、关键词与向量混合检索，以及结合上下文进行工具调用。模型生成的结果还需要经过业务规则和状态校验，涉及发信等操作时加入人工审核，控制实际执行的范围。

后台执行由 Scheduler 和 Worker 配合完成：Scheduler 定时创建任务，Worker 领取并执行。任务状态以 PostgreSQL 为准，RabbitMQ 负责通知；通过租约、心跳和检查点支持故障后的重新领取与恢复，通过去重和状态校验控制重复处理。

存储层则按数据用途划分：PostgreSQL 保存业务数据和任务状态，Redis 保存临时状态，对象存储保存附件原件。右侧的日志、耗时和费用统计贯穿各层，方便定位问题和分析运行成本。

部署时，API、Worker 和 Scheduler 可以独立运行和调整副本数，让交互请求与后台处理分别应对负载变化。

## 第 6 页｜多服务器测试

有了这个拆分之后，我们还想进一步看看，放到多台服务器上会怎么样。

主要关心三个问题：多加几个 Worker，处理速度会不会提高；其中一个停掉之后，剩下的能不能接着处理；多人同时操作，会不会重复创建日程，或者把不同用户的数据弄混。

这一页是我们准备做的测试方案，目前完成的是单节点部署，多服务器的结果还需要继续验证。

## 第 7 页｜实际运行

目前我们已经用真实邮箱跑过收信、模型提取和简历处理，也通过人工审核发送了回复，并在收件邮箱里检查了是否收到。

实际运行中也遇到过超时和模型调用失败，所以我们保留了错误原因，并按规则重试。但发信比较特殊，如果不确定是否已经发出，就要先检查，避免重复发送。

另外，我们也记录了处理时间、Token 用量和费用。压力测试和真实邮件处理是分开统计的，没有统计完整的部分会单独说明。

## 第 8 页｜多端

考虑到大家不一定一直坐在电脑前，我们除了 Web，也做了初步可用的 iOS 和 Desktop 版本，目前还在继续完善。

后面还计划开发 Android 和 HarmonyOS。希望用户在电脑上整理完事情，换到手机上，也能方便地查看和继续处理。

## 第 9 页｜工作台社区

我们也希望，这个项目后面不只是由我们两个人不断加功能。

现在用户已经可以修改工作台的字段、阶段和规则，也能导入、导出模板。之后我们想做一个社区，比如有人整理好了保研套磁或者测评跟进的流程，其他人就可以直接添加，再按自己的需要修改。

社区目前还在规划中。模板可以分享，但读取哪些邮箱、是否发送邮件，还是要由用户自己决定。

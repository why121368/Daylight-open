# Daylight 赛道 B：一等奖目标冲刺方案

计划基准：**2026-10-17 01:35，北京时间**。用户已确认截止为 **2026-10-18 10:30，北京时间**，计划窗口约 **32 小时 55 分钟**。投入为 **2 人 + Codex，总预算不超过 500 元**。本地实施分支为 `feat/competition-evidence-20261017`；最终提交 Commit 仍待冻结。

本文给出执行计划和验收门槛，**不是已完成结果或得分预测**。冲刺目标是让评委看清一个真实、有价值、能解释失败与成本的 Agent 系统；是否获奖取决于最终证据、现场表现及其他队伍。实现与历史验证以 [STATUS](../../STATUS.md) 为准，提交入口见 [材料清单](README.md)。

## 1. 获奖主张与范围

推荐主张：**Daylight 帮助多校并行申请者，把分散通知转成有来源、有前置条件、需要确认并能追踪回执的下一步。** 核心例子不是“读完一封邮件”，而是“收到面试通知后安排时间，遇到改期时保留旧安排、关联新安排，并处理冲突和需要补交的材料”。

演示主线选 **保研价值叙事 + 真实邮件变化闭环**。工作台说明用户为什么需要它，邮件新增、改期、取消及 trace 证明系统实际执行了什么。基础同步与工作台确认是两条不同路径：前者可能直接写入提取到的日程，后者须确认后才写入。两者均需按真实行为介绍，不能拼接成一条代码尚未实现的自动链。

其他场景只用一行说明复用能力。已有发票真实测试作为工程证据附录；招聘的真实模型、OCR 与失败分析作为质量附录。首次登场不展示六种工作台，也不把尚未真实联调的飞书作为必经步骤。

**主线门槛：10 月 17 日 12:00 前作决定。** 保研主线须在提交候选版本完成至少两轮端到端复跑，包含一次新的实际模型调用、来源回查、确认与变更后的正确状态；重复触发不增加记录，未完成前置不能被“已准备”绕过。达不到时，在 13:00 前切换至已验证更稳定的招聘主线；招聘也需实测通过且能在 3 分钟内展示关键执行，否则切换至稳定的基础邮件日历新增→改期→去重链。切换后同步修改 PPT、技术报告摘要和 Demo 讲稿，不能继续承诺未验收的保研自动闭环。

允许少量真实服务联调，但目前测试收件范围尚未明确，**不主动向真实地址发送邮件**。可先做隔离合成样本的真实模型评测、只读检查授权范围内已有测试邮件，以及等待用户明确测试邮箱/收件人后执行受控发信。登记“已发送”回执不等于 SMTP 已发送，不拿人工状态代替投递证据。

## 5. 真正争取架构分：分层交付与扩展包

“没有时间所以只写路线图”不能充分体现工程投入；“写一份 K8s YAML”也不证明云原生正确。基于 [架构与代码缺口](../why_test/01-architecture.md) 和 [技术决策](../why_test/02-technology-decisions.md)，用实际部署、明确状态边界、失败恢复和对照数据争取架构分。

### A 包：必争取的可复现云端单实例

交付应用 Dockerfile、锁定运行环境、完整启动入口、健康检查、HTTPS/反向代理说明、外部配置和持久化方式。API 容器监听、PDF/OCR 原生依赖和语言包需实际验证。现有 `docker compose up -d` 仅启动 RabbitMQ，不能作为完整应用部署证据。

验收：新机器或干净环境按文档启动；登录与核心主线成功；重建容器后业务状态仍在；切回上一镜像可运行；记录镜像 digest、版本、CPU/RSS 和实际依赖。现有 JSON 模式若用于演示，标为单实例开发/演示存储并保留持久卷，不能承诺多实例或生产恢复。PG 路径若启用，逐项核对真实权威状态和故障行为，不把“配置已连接”写成全系统 PG 权威已经统一。

### B 包：高价值扩展——一条可恢复的后台执行路径

在 A 包可用、主线稳定且 B 有余力时，优先实现**主线任务的一条完整纵向路径**：API 保存带用户/邮箱范围的任务→独立 Worker 领取→调用模型/工具→持久记录结果→页面查询进度。复用现有业务模块，不按页面拆服务。

最少契约：任务 ID、固定用户/邮箱、输入摘要/版本、状态、尝试次数、租约到期、步骤结果；PG 原子领取、条件提交与重复请求去重。调度只运行一个明确角色，外部调用不占长事务。必须评估现有写路径：任务持久化不等于日历/待办已经统一事务，若业务结果和任务完成无法原子保存，就要实现可复验的对账/重放保护，或缩小已验证范围。

验收至少包括：领取后杀 Worker 能恢复；完成后重投不重复写；过期 Worker 不能覆盖新结果；双用户任务隔离；PG 不可用时该路径停止执行并显示错误；数据库恢复后已有结果不复活重做。真实 SMTP 的重复与未知窗口优先用受控模拟测试，不拿陌生收件人试故障。

**可选同级扩展：OCR 资源隔离。** 如果真实采样表明 OCR 拖慢 API，可把 OCR 放独立进程并设并发/页数/内存上限，用同一负载比较 API 尾延迟和总资源。只有实际改善且主线不退化才保留。若没有瓶颈证据，先完成可靠任务，不同时推进两项大改。

### C 包：有条件地上 K8s，并证明为什么需要

只有 A、B 通过，且计划部署范围内的会话、权限、业务结果、trace、附件与任务均可跨副本正确读取/写入，才开展多副本。仅新任务用了 PG，而旧 `store`、会话或附件仍依赖本地文件时，不能扩 API 副本后声称高可用。单副本 K8s 可作为部署实验，但不能冒充已验证横向扩展。

真实多副本验收包括：至少两个相关副本承接请求/任务；同邮箱有序、重复确认无重复结果；停止一个实例后任务可恢复；滚动升级/回滚后状态正确；模型额度在副本间共享；数据库故障不静默退回本地权威。记录实际拓扑、资源 requests/limits、探针、重启/恢复时间与失败结果。

弹性伸缩必须用固定副本作基线，随后展示相同有界负载下排队和资源的变化，不能只有 HPA 配置截图。I/O Worker 不能只按 CPU 扩容；模型 RPM/TPM 已饱和时应背压，增加 Pod 不会增加服务商额度。

**停止条件：**10-17 17:00 仍缺共享状态或故障验证，停止扩大部署，交付已经通过的 A/B 范围与其真实数据。保留目标架构和未完成项；这是基于截止的交付选择，不是项目长期规模上限。

## 7. 用户价值实验与效果评测

### 人工基线：3–5 人、交叉顺序、计入核验

招募 3–5 位接近目标用户的参与者，用虚构学校与通知构造两套**难度相近、内容不同**的任务集；每套含明确期限、一次改期、一个冲突、至少一个需要确认的材料/回执。先由人工标注正确对象、时间、动作和完成条件。测试者知情参与，材料不包含私人申请结果。

一半参与者先用邮箱+日历/待办人工完成 A 集，再用 Daylight 完成 B 集；另一半反过来。奇数人数时记录两组差异，按交叉顺序执行，不让所有人先人工再工具。统一任务说明和必要操作教学，不在第二阶段透露正确答案；记录经验差异和求助次数。

从读任务开始，到参与者确认结果可用结束，**人工核验来源、检查日期、修改错误、补漏、等待模型和恢复失败都计入总时间**。另外记录实际操作时间与机器等待，不能只用模型生成速度对比完整人工流程。核对所有关键结果，不把“成功入库”当作正确完成。

保存每人的模式、任务集、执行顺序、开始/结束、总秒数、修正时间、正确项、漏项、误报、未完成及主观反馈。报告逐人结果、中位数和范围；3–5 人不支持稳定的总体 p95 或显著性结论。样本是探索性验证，明确不外推所有保研用户、全年节约时间或市场规模。

### 模型和系统效果

模型评测使用独立数据目录，固定模型配置、提示词/模板版本、北京时间参考时刻和已有日程上下文。人工答案只用于评判，不能注入请求。分别统计关键日期/对象/动作正确、完整任务成功、需要人工修正、拒绝/歧义、超时与格式失败；所有尝试保留，不能删失败后报成功率。

真实模型处理合成输入属于“真实模型评测”；只有实际收件、实际模型、实际写入全部执行才称对应范围的真实端到端链路。模拟外部故障验证是有效工程证据，但要标记模拟。演示样例的预置提取不参加真实模型准确率统计。

性能至少分开邮件读取、排队、模型、OCR、保存和人工等待。若样本足够，给p50/p95及计算方法；小样本直接给逐条耗时、范围和样本量，不以两个观测值包装稳定p95。短 API 负载和外部模型任务分开测，记录机器、并发、运行时长、失败及CPU/RSS；停止条件包括主机过载、错误激增和费用上限。

## 10. 3 分钟真实 Demo：步骤、判定和降级

现场使用冻结版本与受控账号。测试邮件可提前实际送达，原有日程可提前建立并明确说明；至少一个核心分析/工具执行现场真实运行。模型和网络耗时通过排练确认，不能依赖现场临时配置。外发邮件不作为必经步骤，除非测试收件范围和当前路径均已确认。

| 时间 | 操作 | 成功判定 | 超时/失败处理 |
| --- | --- | --- | --- |
| 0:00–0:20 | 展示原通知、申请事项和一条原安排，说明待解决的变更/冲突 | 来源、对象和前置状态清楚；预置初始状态已说明 | 原邮件不可达时打开已保存原文，明确来源已预先读取 |
| 0:20–1:10 | 触发实际分析/处理；展示正在执行的步骤与结果 | 本次trace有真实模型/工具记录；目标和日期正确 | 约40秒尚未结束时简述状态，继续展示可独立验证部分；不反复重试叠加请求 |
| 1:10–1:50 | 核验来源和参数，确认一项行动，展示日历/待办及冲突 | 结果与审核参数一致，未完成前置阻止执行 | 模型出错则演示错误/修正路径；不要口头宣称错误结果正确 |
| 1:50–2:25 | 展示后续变更的新旧关联，或重复触发不增加记录 | 原记录保留取消标记，关联正确；重复处理不新增 | 复杂变更失败时展示明确状态，转已准备的该过程证据，注明它是此前运行 |
| 2:25–3:00 | 打开本次trace、耗时、usage/费用覆盖与待回执状态 | 从来源可回查执行；已完成和等待人工分开 | 未知费用显示未知；不能用历史usage冒充本次 |

降级次序：**同版本已保存来源上的现场实际处理 → 同版本其他稳定核心操作 → 对应失败步骤的备用录屏/历史trace**。明确告知网络或依赖故障，仍尽量保留可现场验证的核心操作。不可用预置结果冒充模型返回，不用录像替代所有可现场运行的核心功能。

若主线已按12:00门槛切换，沿用上述节奏，替换成招聘“附件→分析→来源核验→人工确认后行动”，或基础邮件“新增→改期→去重”；删除与实际链路无关的点击。OCR首次语言包下载、全量历史收信、登录注册和设置配置不放进3分钟主线。

# 答辩讲稿与演示脚本

这是演示内容与排练脚本，尚未生成 PPT 或演示视频。时间均为目标分配，不是已完成录制的时长。发布前按同一冻结 SHA 更新实测证据；未完成的项目直接说待验收。

## 五分钟，八页

### 1 · 从读过通知到完成下一步（0:00–0:30，30 秒）

页面：Daylight；多校申请中的来信、材料、期限、面试、回执五个元素；一句价值主张“让分散的信息，成为可追踪的下一步”。

讲稿：保研申请往往同时跟进多个学校。一封邮件读过了，不代表已经补材料、确认参营或处理面试冲突。Daylight 围绕同一个申请事项，连接通知、材料、行动和回执。我们首先解决多校并行跟进的问题，减少反复查找和遗漏；节省多少时间还需要用户实验，今天不报未经测量的比例。

### 2 · 一个事项，保留完整上下文（0:30–1:05，35 秒）

页面：保研工作台截图位置；来源、阶段、材料版本、前置行动、回执五项标注。使用实际截图前保持“截图待补”文字。

讲稿：每所学校或项目对应一个跟进事项。邮件可以关联到已有事项，也可以建立新事项；官网和群通知可以手动登记。材料补充会保留旧版本，已读、已准备、已提交和对方确认分别记录。保研是主线，申博、求职和投稿复用这套场景模板；招聘和发票则保留各自已有业务页面。

### 3 · Agent 的执行闭环（1:05–1:45，40 秒）

页面：来源 → 上下文分析 → 建议 → 人工确认 → 待办/日历 → 回执；角标“模板规则回放与模型调用分别标识”。

讲稿：系统把来信放进事项上下文，结合材料、期限和已有安排提出建议。规则会阻止把“欢迎报考”当录取，也会保留共同作者确认等前置条件。工作台行动确认后才写待办或日历。这里需要说明，基础邮件同步可能直接写提取到的日程；工作台确认流程是独立语义。小 D 可以准备回复草稿，真实发信还有明确审核入口。

### 4 · 状态和执行如何分开（1:45–2:25，40 秒）

页面：使用 [架构图](architecture.md) 的精简版，保留“代码已写 / 集成待验收 / 云端待验收”标签。

讲稿：前端与 API 接受用户操作，持久任务保存在 PostgreSQL；Worker 负责长任务，Scheduler 按明确的邮箱归属调度。MQ 用于通知，数据库保存权威任务状态。本机已经验证 HTTP 入队到独立 Worker 提交，以及检查点后强杀并重启恢复。使用真实 PG、Redis、MQ 和本地 S3 模拟服务。完整容器栈仍受镜像下载阻塞，云端验收尚未完成。

### 5 · 重试不会自动变成重复操作（2:25–3:05，40 秒）

页面：同键去重、邮箱顺序、租约 fencing、步骤事务、unknown 五个点；一个“确认后进程中断”的失败路径。

讲稿：任务与 outbox 同事务提交，重复通知由数据库 claim 和步骤记录处理。同一邮箱串行，租约过期后旧执行者不能提交数据库副作用。本机强杀恢复未重复行动，八个并发确认仅产生一条日程，注入日历写入失败时场景与日历一起回滚。但数据库事务不能回滚远程 SMTP；如果服务接受后连接断了，结果可能未知，必须保留状态并人工核验。

### 6 · 演示将证明哪些行为（3:05–3:45，40 秒）

页面：通知 → 关联事项 → 核对建议 → 冲突 → 确认 → 回执 → 来源；样例模式标签。

讲稿：接下来的演示会沿着一个事项，展示材料与截止、面试冲突和变更后的保留记录。若使用模板样例，我会明确标注这是预置规则回放；只有现场实际请求已配置模型时，才称为模型分析。发信草稿和实际发送也会分开展示，未得到授权时演示到待审核。任务页面和 trace 用来解释发生了什么，不替代真实外部回执。

### 7 · 性能和成本用证据回答（3:45–4:25，40 秒）

页面：原始 JSONL → 含失败 p50/p95 → 成功/失败/未完成 → CPU/RSS → 费用未知项；标注“本机真实 PG + 合成 handler；云端待测”。

讲稿：我们已运行本机真实 PG 的任务基准，业务 handler 是可控 stub，不调用模型。每组两百个任务，并发一、二、四，各有二十个预设失败。主延迟指标包含失败终态，原始记录完整保留；CPU 和 RSS 只覆盖当前 Node 进程。每档仅运行一次，版本仍有未提交改动，因此这不是云端容量或真实模型性能结论。模型及基础设施费用仍保留未知。

### 8 · 当前交付与下一道验收（4:25–5:00，35 秒）

页面：业务闭环代码、任务与存储代码、部署材料；下一步真实整链、故障恢复、云端容量、用户价值评估。

讲稿：当前交付重点是可追踪的申请事项和有明确失败语义的执行基础。已有本地业务验证历史，新云原生改造按实际集成结果逐项验收。下一步要完成同版本的干净部署、真实邮件与模型闭环、故障恢复及容量测试，再通过用户对照实验量化价值。在线地址、冻结版本和备用视频只有实际完成后才填入提交材料。

## 七分钟 Q&A 排练（七题，每题约一分钟）

1. **与邮件摘要或普通日历有什么区别？** 答：摘要帮助读懂一封信，工作台持续记录一个申请事项的材料版本、前置行动、变更和回执。具体比较应看“补材料后是否保留旧版本”“改期后能否回查原安排”“未提交能否误标完成”。目前这是已实现的产品行为目标，节省时间的幅度需要真实用户对照，不能用功能数量代替效果。
2. **为什么称为 Agent？模型做什么，规则做什么？** 答：模型结合上下文提取与分析并提出行动，工具执行查询、日程或草稿操作；规则限制阶段、材料及前置关系，人工确认约束外部动作。展示 trace 才能说明某一次调用实际用了哪些工具。规则样例没有模型推理，必须单独标识；系统不执行邮件中的指令。
3. **是否已经云原生和生产可用？** 答：目前有共享状态、持久任务、独立角色和部署清单的代码建设，但这不等于完整云验收。回答时展示冻结 SHA 对应的发布清单，明确哪些是单测、真实依赖、云端或生产验收。尚缺的干净部署、故障恢复、扩缩容和容量证据如实列出，不能引用历史本地测试代替。
4. **Worker 重启会重复执行或丢任务吗？** 答：任务先持久化，通知只是唤醒；租约到期可恢复，旧 token 被拒绝，数据库 checkpoint 可以避免重复数据库副作用。MQ confirm 与 outbox 更新之间仍可能重复通知。外部模型可能重复计费，SMTP 可能结果未知，不能承诺端到端 exactly-once；这些需要提供方幂等或人工核验。
5. **如何保护不同用户的邮箱与附件？** 答：API 身份来自登录上下文，读取和修改任务按 tenant/owner 范围过滤，同时校验邮箱；Worker 重新核验任务归属，不能依赖进程当前活动邮箱。附件和业务存储也需要同样检查。给出双用户、跨邮箱和撤权后的真实 HTTP 测试记录；没有经过全链权限验收就不把单个仓库断言扩大成全系统保证。
6. **能支撑多少并发，费用多少？** 答：当前没有可发布容量结论。脚本对真实 PG 测调度与持久化，stub 等待和失败是实验输入；结果包含失败和未完成，并记录单进程资源。它不测真实模型吞吐。正式费用由实际 usage、单价、云实例时长和账单构成，未知项保留未知。扩容还受邮箱顺序与外部配额限制。
7. **商业化与下一步验证是什么？** 答：先验证多校申请者是否更少遗漏、是否更快找齐材料和核对安排，再评估付费意愿。可用同类任务人工基线对照操作时间、漏报误报和回执完成率，样本与失败案例一并公开。招聘等场景复用基础能力，但不能用场景数量替代目标用户验证；真实闭环、成本与可靠性通过后再决定运营规模。

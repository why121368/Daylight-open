# 分布式状态、任务与 Agent 执行可靠性设计

> 设计日期：2026-10-17（北京时间）。本文是目标方案与实施验收约束，不是已实现或已完成云端验证的说明。本次只编写文档，不迁移数据、不调整运行配置、不连接真实依赖，也不触发模型、邮件或会议操作。当前实现及历史验证以 [STATUS](../../STATUS.md) 为准。

供应商优先级已调整为优云智算：本文US3优先指CompShare云存储的对象接口，ModelVerse优先承担经验证的模型调用；PG仍按原事务契约由合适服务提供，不能因平台选择改用本地文件权威。CompShare与外置PG的网络及账号边界见 [04](04-deployment-and-capacity.md)，模型具体契约见 [06](06-compshare-service-plan.md)。

## 1. 先解决状态一致性，再增加副本

Daylight 的难点不是让几个容器同时运行，而是保证两个用户同时修改日历、同一邮件重复投递、Worker 在发信后退出时，系统仍能说明“做过什么、还欠什么、哪些结果不知道”。因此首期生产方案以 PostgreSQL 为业务与任务账本，附件内容放私有 US3，API、调度、I/O Worker、OCR Worker 共享同一套业务服务与存储契约。运行职责可以拆开，代码仍维持模块化单体、单仓库；不先把日历、工作台、招聘拆成各自拥有数据库的微服务。

这样选择的直接收益是：工作台确认、日程或待办写入、邮件处理标记和任务登记可以在一个短事务内提交。代价是数据库成为共同依赖，必须管理连接数、索引、备份、租户公平性及长事务。独立微服务加独立数据库会把这些操作变成跨服务一致性问题，目前没有团队边界、独立发布频率或容量证据来抵消这笔成本。

## 2. 状态所有权与存储边界

首期租户边界采用现有用户拥有邮箱的模型：`tenant_id` 可映射为现有 `ownerUserId`，邮箱仍有独立 `mailbox_id`。这不是声称已支持企业共享租户；未来组织协作需要明确成员、角色与邮箱授权表之后才能开放。旧数据缺失归属时单独待认领，不默认暴露给任何登录用户。

| 状态 | 唯一权威 | 写入所有者与约束 | 可重建部分 |
| --- | --- | --- | --- |
| 账号、角色、邮箱归属、配置版本 | PG | 认证/配置模块，版本检查与审计 | 配置的非敏感读缓存 |
| 会话、撤销版本、验证码/重置挑战 | PG | 认证模块；挑战一次性原子消费 | 会话显示信息可缓存；不能靠缓存决定是否仍获授权 |
| 邮件、处理状态、日程、待办、发票 | PG | 邮箱业务服务；统一事务和版本 | 前端视图、检索摘要 |
| 工作台、事项、材料、行动、人工回执 | PG | 场景服务；跨模块调用传入相同事务 | 看板统计 |
| 候选人、邀约、草稿、会议操作及发送凭证 | PG | 招聘/助手服务使用公共副作用协议 | UI 展示缓存；`sent/unknown` 等关键状态不可当缓存 |
| Job、步骤检查点、重试、幂等键、审批、outbox | PG | 执行模块；唯一键、租约、条件更新 | 队列唤醒通知 |
| 附件原件与必要的大体积产物 | 私有 US3；PG 持有对象版本和归属 | 附件服务；不可变对象、引用与清理协议 | Worker 本地临时副本 |
| OCR 文本、RAG chunk、向量及索引版本 | PG 起步，必要的大文本可关联 US3 | 检索服务；显式来源、版本和权限 | 可由保留的原件重建；删除/撤权标记不能丢 |
| 提示词当前版本、修订、模板快照 | PG | 配置/模板模块 | 进程只缓存不可变的具体版本 |
| 执行证据、用量与成本估算 | PG 保存必要业务证据，运维日志另行采集 | 执行模块，默认脱敏 | 观测聚合；未知 usage 不能补成零 |

首期允许把变化较快的场景字段继续放 JSONB，但所有记录增加租户、实体 ID、版本、时间和必要索引；需要唯一性、关联与竞争控制的 jobs、effects、approval、sessions、邮件身份、日程至少拆成独立行。不要把所有用户或所有邮箱持续写进一条无版本的大 JSONB。也不必为每个模板字段立刻建表。

Redis 首期可不部署，前提是完成上表中的 PG 会话与验证挑战改造。以后只在实测高频限流、非关键缓存或通知需要时引入。Redis 丢失允许导致缓存未命中，不能让已撤销会话复活、验证码再次使用、已发送邮件重新排队。生产 PG 不可用时，拒绝新业务写入和副作用；UI 可以展示明确标明时间的已有只读快照，不把本地 JSON 作为新权威。

## 3. 跨入口事务、版本与邮箱顺序

### 3.1 一个逻辑动作一个提交点

手动日程、基础邮件同步、小 D、招聘邀约、场景确认、外部日历回写都使用同一邮箱写入服务。事务完成以下工作：重新读取当前记录和版本，验证授权/业务前置，写业务变化，更新处理状态，登记需要异步执行的 jobs/outbox，再提交。使用统一、稳定的锁顺序；遇到死锁或版本冲突，只对尚无外部动作的短事务做有界重试。

例如工作台“确认改期”应在同一事务内：核验行动版本和前置回执 → 锁住对应邮箱的日历版本行 → 将原日程标为 `cancelled` → 创建新日程 → 设置 `previousEventId/replacementEventId` → 回写行动关联 → 登记外部日历推送 job。中途失败不留下“原安排已取消但新安排丢失”的半成品。外部日历推送独立重试，失败写连接 `lastError`，保留已提交的本地安排。

模型和外部网络调用都在事务外执行。提交时携带 `expected_version`；若从模型读取上下文到提交期间日程被手动修改，重新校验或生成新建议，不能整份覆盖旧快照。比较的版本包括相关业务记录、配置、模板和审批版本，不用客户端时间戳作为写冲突仲裁。

日程冲突是现有产品允许人工核验的业务提示，不能擅自加“一切重叠都禁止”的数据库约束。所有入口先锁同一邮箱日历版本行，在最新快照上计算冲突；需要用户确认时返回冲突与版本，确认只对该版本有效。飞书等长调用前可写带期限的暂定占用，避免另一入口同时忽略该计划；它不是已经成功的会议。取得外部链接后提交前再核验，冲突则保留外部结果进入待处理，不能丢弃链接后重新创建。

### 3.2 保留当前邮件业务语义

1. 去重继续以现有邮件 ID 为业务依据，建立 `(tenant_id, mailbox_id, source_email_id)` 唯一约束；迁移不重算历史 ID。另保存文件夹、IMAP UIDVALIDITY/UID 等同步游标。邮箱不同、文件夹或 UID 世代变化时不能仅按 UID 合并；Message-ID 缺失或重复需保留原始定位证据。
2. 每个邮箱同时只允许一个修改邮件业务状态的同步序列，不同邮箱可并行。批次内按邮件时间从早到晚处理，同时间以稳定定位符排序；下载/OCR 可以并行准备，但模型分析与依赖现有日程的提交按序。保留当前单封失败或待匹配后继续处理其他邮件的行为，不把一封失败升级为整个邮箱必须人工解锁的阻塞。`SKIP LOCKED` 不能让两个 Worker 同时提交同一邮箱的变更；若后续动作明确依赖某个未完成步骤，仅该依赖链等待，目标不明确则记失败并保留重试能力。
3. 自动重试仍遵循最近 N 封范围规则；历史失败重试和新一批发现更早的邮件都用当前日程重新分析，不把已执行历史倒放一遍。跳过或人工处置保留原因，但不新增“每次失败都必须人工跳过”的前置条件。完整历史的严格顺序无法仅靠“最近 N 封”保证，界面和证据应保留覆盖范围；若未来要改成失败即阻塞整条邮箱流，应作为独立产品策略评审。
4. 成功和明确跳过的邮件不再提取；失败仍可重试。`create/cancel/reschedule`、取消保留原记录、改期双向关联、旧数据无 `status` 视为有效都保持不变。示例只能影响示例日程，真实邮件可匹配真实或手动日程，目标不明确不提交。
5. 工作台建议仍先确认后落日历/待办；基础同步已有直接入历行为不因迁移而偷偷改成全部人工审批。工作台人工“已发送”回执与 SMTP 实际发送保持不同字段和证据来源。
6. 时间保存可比较的绝对时刻及必要的原时区，业务展示、日期规则仍用 `Asia/Shanghai`；全天结束为最后一天的次日零点。不得按容器所在时区解释时间。

## 4. 首期任务协议：PostgreSQL jobs，必要时才加消息代理

### 4.1 为什么先使用 PG jobs

现阶段主负载是邮箱轮询、模型 I/O 与有界附件处理，业务数据本来就需要 PG。把业务变更与 job 插入同库提交，直接消除“业务成功但忘记投递”的窗口，少运行一个必须可靠的系统。Worker 使用短事务领取到期任务，按种类和租户公平取任务，任务执行期间不占用事务连接。代价是轮询与任务更新会增加 PG 写入和 vacuum 负担，需要索引、归档及负载测量。

这里不采用“业务提交后直接发 RabbitMQ 就足够可靠”的方案；数据库与代理没有共同事务。也不把现有 `jobs` 内存数组当作任务账本。Kafka 更适合有长期高吞吐事件流与多订阅重放需求的场景，目前没有该证据。完整工作流引擎可在跨天流程、人工任务和版本恢复复杂度显著增长时评估，首期不为框架重写已具备的业务状态机。

### 4.2 逻辑字段与状态

下表是设计字段，不是可执行建表脚本；表名可在实施时适配现有仓储。

| 记录 | 关键字段 / 约束 |
| --- | --- |
| `jobs` | id、tenant/mailbox、kind、payload_ref、dedupe_key、status、available_at、attempt/max_attempts、lease_owner、lease_until、fence、deadline、result_ref、error_class；幂等唯一键有租户与任务语义范围 |
| `job_attempts` | job_id、attempt、worker、开始/结束、检查点、模型/配置版本、错误与 usage；一次重试一条记录 |
| `mailbox_leases` / `sync_runs` | 邮箱、同步范围、稳定排序、当前序号、租约、fence、配置版本；同邮箱只有一个有效推进者 |
| `effects` | operation_id、kind、业务唯一键、请求摘要哈希、审批版本、状态、外部 request/message ID、接受/拒绝回执、恢复说明 |
| `approvals` | user/tenant/mailbox、动作种类、目标、完整参数哈希、内容版本、相关实体版本、批准时间、有效期、消费状态 |
| `outbox`（需要代理时） | event_id、job_id、版本、目标、待投递/已投递、次数、下次时间；消息只放 ID 与版本，不放凭据、正文或 PDF |
| `run_events` | run_id、递增 seq、tenant/mailbox、事件类型、脱敏 payload；`(run_id, seq)` 唯一 |

任务基本状态为 `queued → running → succeeded`，另有 `retry_wait`、`failed`、`cancelled`、`waiting_approval`、`unknown`。`unknown` 是需要核验的业务状态，不是下一次自动重试的同义词。认证失败、内容校验失败与模型格式长期不合法不应无限重试；429、短暂网络失败按提供方 Retry-After 或有界指数退避加抖动处理，并受租户预算、最大次数及业务截止约束。

完成任务可归档，但幂等记录、已发事实与 unknown 待核验记录不能跟随普通进度日志短期删除。保留期覆盖业务允许的重放与备份恢复窗口；超期请求返回已归档/需核验，不能把“查不到任务详情”当作从未执行而新建同一外发动作。清理策略在上线前与产品留存及备份策略一并确定。

调度器先使用单副本运行，但用 `(mailbox_id, schedule_slot, schedule_version)` 唯一键防重，滚动发布或失效接管也不重复登记。自动触发和手动同步可合并为同邮箱的待处理请求并保留各自来源，不能产生两个并行写入者；错误配置不通过“加大副本数”绕过邮箱串行规则。

### 4.3 领取、续租与 fencing

Worker 在短事务内以 `FOR UPDATE SKIP LOCKED` 选择可运行任务并写入 `lease_owner`、数据库时钟计算的 `lease_until` 和递增 `fence`。对邮箱有序任务还须取得邮箱租约，并检查当前可推进序号；`SKIP LOCKED` 本身不保证业务顺序。Worker 在任务运行期间按协议续租，更新进度和提交结果必须携带相同 owner/fence，且租约仍有效。

接管时 fence 增加，迟到的旧 Worker 即使随后恢复也不能提交结果；失去数据库连接就停止领取和开始新步骤。对 OCR、模型读取等可重算步骤，租约失效后新 Worker可以按持久检查点继续，重复计算的成本计入 attempt。参数相同不意味着模型结果恒定，已确认的业务结果不能被后来的重复计算覆盖。

**fencing 只能保护理解该令牌的本地状态写入，SMTP、IMAP 或第三方 HTTP 服务通常不理解它。** 发信已经标记 `dispatching` 后的租约超时不能直接重投；旧进程可能仍在向远端发送。必须进入下一节的外部副作用核验流程，先隔离旧执行者并确认结果或人工处置，不能声称数据库租约实现了“外部恰好一次”。

扩缩容时 Worker 停止领取，完成可结束的短步骤并保存检查点；超过退出宽限的 OCR 可重算，处于外部发送窗口的任务进入待核验。运行职责拆分的价值在这里：OCR 进程 OOM 不应同时抹掉 API 会话或整个同步调度状态。

### 4.4 RabbitMQ 的进入条件与接入方法

只有容量测试显示任务轮询/领取显著占用 PG I/O、调度延迟达不到业务目标，且索引、批量领取、退避、归档后仍不足，或者确有多个消费者组与独立背压需求，才评估 RabbitMQ。不能仅因仓库已有 `amqplib` 就把它设为首期必选。

引入后 PG 仍为任务权威：业务事务同时写 jobs 与 outbox，发布器使用 publisher confirms 后标记已发布；发布成功但标记失败允许再次发布。消费者按 job ID 检查幂等与领取状态，业务结果持久化后才 ACK。重复消息正常处理，毒任务进入有记录的失败/死信流程。发布器、消费者和回收器都有恢复点；禁止代理故障时偷偷换成内存队列执行。若需要 PG 直接领取降级，应是预先设计并验证的同一 jobs 协议，不能与另一套执行器争抢副作用。

## 5. 审批、工具授权与外部副作用

### 5.1 模型输出不构成授权

API 从已认证会话生成固定的执行身份与邮箱范围；job 只记录身份、配置版本和凭据引用，Worker 按 job 的服务身份加载数据，不依赖请求线程的 AsyncLocalStorage 或当前活动邮箱。模型返回的 tenant/mailbox、路径、收件人或工具名都需要服务端校验，邮件正文与 RAG 文本始终是待分析数据。

ModelVerse API Key、CompShare计算资源API凭据、US3 Token和数据库凭据分别管理，不因“统一账号”而合并为同一个万能密钥。服务端按租户/用途保存选定模型、模型能力测试版本、endpoint、配置版本与凭据引用。修改服务商或模型仅影响显式选择的新任务；重试仍遵守原数据用途授权与预算，历史usage和价格快照不改写。平台额度按实际key/账号范围协调，避免每个Worker各自获得完整配额。

审批绑定完整发件人、全部收件人、主题、正文及附件版本、操作种类、目标邮箱、相关日程版本和参数哈希。内容、邮箱或相关安排变化就失效并重新审核。开始副作用的短事务中重新检查会话/授权策略、邮箱归属、审批有效性和版本，同时将审批消费与 effect 状态推进提交。模板声明了能力不等于用户批准发送；小 D 草稿、招聘邀约、普通回复和系统邮件都要明确自己的触发权限，不能只有小 D 一条路径受到保护。

撤销授权或删除邮箱时取消尚未派发的动作并阻止新步骤；已经提交发送意图并在远端执行的动作进入核验流程，不能承诺撤销点击能收回已发邮件。对话请求取消、job 取消、撤销审批和撤回远端结果是不同操作，界面分别呈现。

用户明确要求创建会议的请求可作为该次会议动作的授权证据，仍不等于授权随后发邀约。系统验证码邮件由用户发起注册/重置流程授权；其重试、频率和收件人限制属于认证服务，不复用任意模型发送权限。向量化或模型分析也必须受已开启功能、调用预算和模型配置限制。

### 5.2 SMTP 结果未知必须保留

对 [assistant-actions.js](../../server/assistant-actions.js) 已有 `sending/unknown`、草稿版本与完整收件人回执语义做统一推广：

| 阶段 / 结果 | 目标处理 |
| --- | --- |
| 审核中，尚未开始发送 | 可修改；修改后审批失效 |
| 已批准，准备调用 SMTP | 短事务持久化参数快照、Message-ID、审批消费与 `dispatching`，提交后才连接远端 |
| 明确在认证、连接等未接受阶段失败 | `failed_unsent`，说明证据，按原产品交互重新审核后重试 |
| 所有收件人得到 SMTP 接受回执 | 保存 accepted/rejected、Message-ID 和发送时间；UI 沿用“已发送/服务已接受”含义，不宣称送达或已读 |
| DATA 后断连、超时、部分接受、接受后回执无法保存、执行者失联 | `unknown`，禁止自动整封重发，保持逐收件人证据 |
| 用户/运营核验 | 记录证据、操作者与结论；确需重发时产生新的明确授权操作，仍保留原 unknown 记录及重复风险 |

固定 Message-ID 有助于检索和核验，但 SMTP 没有普遍可靠的幂等键保证，不能把它当成远端去重协议。发件箱没有找到邮件也不是“肯定没有发送”的证据；部分接受时只向确定未发送的收件人准备新草稿，并单独审核。旧 Worker 未被隔离时不可因为“人工核验后还没看到”就启动另一次发送。

第三方会议、外部日历按能力分类：提供经验证的幂等键或按 operation ID 查询时，可据该协议恢复；没有该能力则先持久化操作意图，未知时核验。已拿到会议链接后本地写日程失败，只补本地日程和草稿，不再新建会议。外部系统无法回滚的步骤不能用“撤销本地事务”假装回滚，补偿动作本身也需要权限、状态与证据。

## 6. SSE、跨实例恢复与执行证据

前端首次提交使用稳定 `requestId`，服务端以 `(tenant_id, mailbox_id, requestId)` 唯一登记请求，并保存输入哈希；同 ID 不同输入返回冲突。同 ID 同输入只返回已有 run，不能因为 SSE 断开重新调用模型和工具。API 负责展示与订阅，Worker 负责执行，浏览器离线不取消已获授权的后台动作。

关键阶段事件先写 `run_events` 再通知，SSE `id` 使用该 run 的序号；客户端按序号去重，并通过 `Last-Event-ID` 或显式 cursor 续接。任意 API 副本先验证当前用户仍有权限，再查询 PG 中 cursor 之后的事件。超出保留窗口返回最新状态/结果快照和新的游标，不自动重新执行。通知可用 PG LISTEN/NOTIFY 作唤醒，之后如有需要用 Redis pub/sub；二者都只提示“去读取”，不能充当可靠事件账本。

令牌级文字流可短暂缓冲并聚合，不要求每个 token 单独落 PG；若此类片段未持久化，重连只保证关键步骤、已提交结果和最终答复恢复，UI 明确丢失片段，不拼造中间输出。完成事件必须晚于最终结果持久化；浏览器切换邮箱关闭旧订阅，旧 run 仍属于最初邮箱。

Agent 恢复以步骤检查点为界：每一步记录工具名、经校验参数摘要、输入/模型/提示词版本、输出引用、授权、attempt 与 usage。纯分析步骤可有界重试；已完成工具读取保存结果；未知副作用暂停。不可从头重播整段对话来“恢复”，否则会再次创建日程或发送。日志不保存凭据或整段邮箱正文，不要求或存储模型私有思维链；业务证据与运维日志分别定义可见范围、留存和删除规则。

## 7. 多租户、会话与 RAG 权限

API 每次按已认证用户解析邮箱，仓储与工具始终携带 tenant/mailbox；SQL 查询、唯一约束、复合外键、对象映射、缓存键、幂等键和 SSE 查询都带同一范围。平台管理员的运维权限不自动变成任意租户正文读取权限，必要的授权访问需要审计。

首期把活跃会话迁至 PG `sessions`：jti、user、session_version、expires_at、revoked_at。JWT 签名有效只是第一层，每次鉴权还确认会话/账号未撤销、未过期；所有副本使用受控的签名密钥版本。密码修改、账号停用与 session_version 更新/会话撤销采用事务；过期清理不影响鉴权正确性，查询本身检查过期。会话 lastSeen 写入可节流，不能每次页面请求都产生热点更新。

验证码和重置挑战保存用途、目标、哈希、过期、失败次数及消费状态；用事务行锁或条件 UPDATE 原子消费，校验和消费不得分成可竞争的 GET/DEL。注册成功与验证码消费、密码变更与重置 token 消费应在一个业务事务内完成。加密/哈希选择应考虑六位验证码的低熵，使用带服务器密钥的校验方式及尝试次数限制，不把普通裸哈希当作防离线猜测保护。PG 不可用时拒绝认证与新副作用，不创建只存在一个副本内存里的临时会话。

PG RLS 可以作为纵深防护，首期多租户上线前应覆盖含租户数据的目标表，并在事务内设置经验证的租户上下文、连接归还时不残留。普通 API 数据库角色不能绕过 RLS；后台作业使用受限服务角色和显式租户范围。RLS 不替代应用鉴权，也不意味着现有表已经配置过策略。

[rag/retrieve.js](../../server/rag/retrieve.js) 已按邮箱过滤，但目标设计还要求：

- 查询先取得允许的邮箱/附件/候选人集合，在 SQL/向量检索阶段限制，再进行相关性排序；不能先全库召回敏感文本再交给模型过滤。`candidateIds` 只缩小集合，不能扩大邮箱范围。
- chunk 同时保存 tenant、mailbox、attachment version、来源页码、候选人、提取器版本、embedding 模型与维度。更换模型或附件版本建立新索引代际，完整后切换可见版本；避免目前“先删后逐条插入”造成半索引可见。
- 生产记录缺失归属时拒绝返回；历史无 mailbox/owner 的兼容数据需迁移核验，不能长期沿用“字段为空也可见”的便利逻辑。
- 引用的页码、摘录和附件预览请求再次鉴权，私有 US3 对象不能因引用 ID 可猜就直接公开。工作台能力关闭或来源撤权后，检索、引用与异步 job 一并检查最新授权。
- 关键词检索是首期基线；向量开启后只将授权范围文本发给已配置的 embedding 服务，记录预算。pgvector 是否可用、维度和索引方式均需按选定服务验证，不将当前可选扩展尝试视为已完成云端向量检索。
- 删除原件/候选人时先提交墓碑和权限不可见状态，再异步清理对象与索引；缓存/向量库的旧结果必须受墓碑过滤。留存期内的审计仅保留必要元数据，不能成为绕过删除的正文入口。

## 8. PostgreSQL 与 US3 无共同事务时的协调

优先CompShare华北二A/上海二B的对象云存储，直接使用经验证的私有US3/S3接口。其他区域“云存储Pro”是POSIX文件服务，不能当成S3，也不能仅因支持共享挂载就拿来存PG数据目录；其多客户端文件能力不会修复JSON读改写或提供数据库HA。

本次读取的[US3 S3文档](https://docs.ucloud.cn/ufile/s3/s3_introduction)明确不支持Versioning，因此本节“对象版本”默认是**应用生成的不可变key/内容代际与PG映射**，不是服务商`VersionId`。不同内容写不同key，旧key保留到备份恢复窗口结束；恢复从独立备份找回所需key，不依赖桶历史版本。若未来使用其他存储的版本功能，须单独验证并声明。对象传输默认HTTPS；公开文档提示内网endpoint不支持HTTPS，不能在程序中静默降为HTTP。账号/token归属、私有访问拒绝、摘要、Range与删除必须实测。

附件对象使用不可变键，PG 元数据保存 tenant/mailbox、content hash、大小、MIME、对象 key/version、扫描/提取状态。桶保持私有；预览经鉴权代理或短期签名 URL，签名参数绑定具体对象而不是任意用户输入的路径。招聘与通用附件都要迁入同一抽象，不能只有通用附件经 [infra/oss.js](../../server/infra/oss.js) 上传，而招聘仍依赖容器本地 PDF。

上传协议为：PG 登记 `uploading` 元数据及操作 ID → 上传不可变对象 → 校验大小和内容哈希/对象版本 → PG 短事务将附件置 `ready` 并登记 OCR job。只在 `ready` 后让下游处理。对象已上传但 PG 提交失败，会留下不可见的孤儿；协调任务按 operation ID 查询、校验并补提交，超过明确宽限且确认没有引用才清理。对象上传失败时保留可重试状态；不能将空文本标为提取成功。

删除协议反向采用墓碑：PG 先标记不可见并登记删除任务，Worker 再删对象和衍生数据。恢复/备份保留期内避免物理删除仍被可恢复数据库快照引用的对象；清理必须理解对象版本与保留窗口。对象 ETag 不一定等于内容 MD5，不能用它替代明确的端到端校验。

原件下载、PDF/OCR 只在有大小、页数、时间及临时磁盘上限的 Worker 工作目录进行；成功后清理临时副本，Pod 更换不会丢失权威原件。US3 不可用时延迟附件处理；纯结构化日程读写可按依赖范围继续运行，不把一次附件失败升级为整个租户数据损坏。

## 9. 迁移、回滚与恢复歧义

### 9.1 迁移步骤与停止条件

首期选择可控维护窗口内的单写切换，比临时开发一套双向持续同步更易验证。若以后实测停机窗口不可接受，再独立设计增量迁移；不能把现有异步双写当作增量迁移协议。

1. **盘点与冻结。** 列出各邮箱/用户的 JSON、`daylight.sqlite`、提示词、招聘附件、外部日历连接、助手权威标记与现有 PG 行；不输出凭据或正文到迁移日志。停止全部 API 写入口、调度和 Worker 领取，等待可安全结束步骤；发送/会议中的操作单独核验。记录冻结点及所有未知操作。
2. **备份与归属核验。** 保留只读快照及文件清单/哈希；对比 PG 和本地数据，按已知权威规则判断。已有 `.postgres` 标记的助手状态必须从 PG 取；不存在通用的“updatedAt 最大者总是正确”。来源冲突、缺失归属、损坏记录单列待处理，不能自动把空集合覆盖有数据的一侧。
3. **导入暂存区。** 保留历史 ID、取消/改期链、草稿版本、发送/unknown 状态、人工回执、示例标记和时区；导入 sql.js 的提示词修订和 kv，明确当前提示词版本。上传附件并核对哈希，建立对象引用。导入记录可重复执行但不覆盖已经确认的新权威结果。
4. **验证完整性。** 核对按租户/邮箱的数量、ID 集合、必要内容摘要哈希、前后关系、唯一键、权限、会话与迁移失败清单；附件抽样读取，关键未知/已发操作逐条核对。会话可选择统一失效并要求重新登录，避免把内存活跃状态伪造为可迁移会话。
5. **切换权威。** 在部署配置与 PG 迁移账本记录 schema/authority version；生产启动强制校验，禁止 bootstrap 从 Pod 本地文件自行导入。先开放只读核对，再恢复受限写入/任务。云端原件与 PG 都完成迁移验证后才能允许多副本。
6. **观察与归档。** 核对新写入、幂等、权限及用量，留存原始只读备份到约定期限；本地 JSON/sql.js 不再接受生产写入。迁移未完成的数据不静默遗漏，界面明确不可用范围。

### 9.2 代码回滚不等于数据回退

数据库变更采用先增加兼容字段/表、再迁移读写、最后在后续版本删除旧结构的方式。上线前验证前一应用版本能读取迁移后的 schema；回滚镜像时仍连接当前权威 PG。禁止将旧镜像连回旧 `data/`，也禁止把停用 PG 当作回滚开关。

如果确实要恢复为文件模式，必须停止全部写入、从最新权威 PG 导出完整状态、处理进行中副作用、验证文件模式兼容，再单实例启动。这是一次有计划的数据迁移，不是数据库故障时的自动动作。对已发邮件、已建会议等事实无法通过恢复文件回到“未发生”。

### 9.3 恢复点之前与之后的外部事实

PG 备份/PITR 只能恢复数据库，不能回滚外部邮箱、会议或 US3。假设数据库恢复到 10:00，10:00–10:10 已被 SMTP 接受的邮件可能在恢复后的库里再次显示待发送，甚至其发送意图完全不存在。仅扫描恢复后仍为 `sending` 的记录无法找全这段风险窗口。

恢复时先隔离旧集群/旧 Worker，关闭调度和一切外发，切换部署执行世代；恢复 PG 与对应对象版本后，把恢复窗口内可能涉及的租户/邮箱副作用置为待核验范围。结合可用的独立审计记录、邮件服务记录、飞书查询与用户确认重建结果，再有选择地恢复操作。没有可靠证据时保持 `unknown`，不能以“备份里没有”推断从未执行。执行世代控制还必须防止旧节点用旧数据库连接继续写入或向外发送，单改 PG 内字段不够。

需要同时保存备份索引、对象版本/保留策略、配置与加密密钥可恢复性、发布版本和恢复检查单。外部副作用审计可降低不确定窗口，但同样存在写入时序与损失边界；除非提供方支持经过验证的幂等查询，不能承诺恢复后外部效果恰好一次。业务 RPO/RTO、备份保留期和审计保留期由本目录部署与验收方案统一定义并实测，本文不另设数字，也不宣称已达到某个时长。

CompShare实例系统盘与镜像不承担上述权威备份：实例删除/关机回收可能释放系统盘，云存储又不随镜像保存。账户欠费还可能同时影响计算、模型和对象访问，是需要余额告警与独立可恢复备份的相关故障；“对象独立于实例”不等于独立于账号欠费或删除。不能只重建计算节点就宣布恢复完成。

## 10. 进入多副本前的可复验门槛

以下为未来实施的测试设计，本次未执行。先用合成数据和可控服务验证协议，再在授权范围内做真实 PG/US3/邮箱/模型与云端故障验证；本地模拟通过不能代替真实验收。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 两 API 同时手动改日程，邮件同步/小 D/工作台同时写同邮箱 | 无丢更新；冲突能返回具体版本；改期链与行动关联一次提交 |
| 调度重复、消息重复、领取后 Pod 退出 | 同业务幂等键只有一个有效结果；任务有恢复记录；同邮箱顺序不被跳过 |
| 租约过期后旧 Worker 恢复 | 旧 fence 无法提交；若已进入外发窗口则进入待核验，不启动第二次发送 |
| SMTP 接受后断网、部分接受、保存回执失败 | 保留 unknown 与逐收件人证据，不盲重发；其他发送入口执行相同协议 |
| 两副本校验同一验证码、撤销会话后请求落另一副本 | 验证码最多成功消费一次；撤销后访问被拒绝；PG 中断无内存放行 |

# 技术选型：收益、代价、替代方案与改变条件

日期：2026-10-17。本文所有“选择”均指目标设计；现有接入、待实现和待验证的区别见 [架构基线](01-architecture.md)。不以已经安装某个依赖包作为继续使用它的充分理由。

本次将**优云智算 CompShare 优先**作为资源选型约束：先采用其满足需要的模型API、无卡计算和对象存储，缺失或未满足可靠性/网络要求的能力再以UCloud标准云补齐。优先级不等于强制租用GPU或把所有UCloud产品写成CompShare内置服务。公开产品事实与待验证接口详见 [06](06-compshare-service-plan.md)。

## 1. 选型依据

Daylight 的主要负载是邮件/模型等网络等待、带权限的状态读写，以及少量但可能昂贵的 PDF/OCR 处理。主要风险是待办或日程遗漏、跨用户泄露、重复外部动作和无法解释的失败。设计优先级为：**业务正确性与授权边界 → 可恢复性 → 可观测性 → 性能与成本 → 更大规模部署**。

评审每个新增组件时回答四件事：它解决当前哪项问题；能否用已有组件达到同样目标；增加多少状态、部署及故障恢复工作；什么实测结果允许保留或撤掉它。没有负载数据时选可演进、可测量的方案，不宣称它是任何规模下的最优解。

## 2. ADR-01：保留 React、Node.js 与 Express

**选择：**保留现有 React/Vite/shadcn 前端与 Node.js/Express 服务；后续在当前支持的 Node LTS 中固定经过验证的镜像版本和依赖锁定文件。当前 `package.json` 的 `>=22` 不是镜像版本锁定。

原因是 IMAP、SMTP、OpenAI 兼容调用、权限校验和业务测试已经围绕此栈实现。I/O 等待用 Node 异步机制即可处理，首要瓶颈通常是模型额度、邮箱连接和存储正确性，不是语言执行速度。把 OCR 移到隔离进程即可避免它与 API 争用事件循环和内存。

| 替代方案 | 现在不选的原因 | 重新评估条件 |
| --- | --- | --- |
| Go 全量重写 | 重建邮件与业务语义成本高，未证明 API CPU 是瓶颈 | 特定连接管理组件经 profiling 证明有明显 CPU/内存收益，独立替换该组件 |
| Java/Spring 微服务 | 适合成熟组织平台，但当前增加开发与部署体系 | 团队已有统一 Java 平台且跨团队维护收益明确 |
| Python/FastAPI 全量替换 | 能调用模型不构成重写理由；增加两套接口与测试维护 | 某项 OCR/ML 依赖仅有成熟 Python 实现时作为后台处理器接入 |
| Next.js/SSR 重构前端 | 当前主产品是登录后的工作台，SSR 不解决任务可靠性 | 公共站点 SEO/首屏指标明确需要时只改公共站点 |

代价是需约束同步文件操作和 CPU 密集操作，监测事件循环延迟、RSS、连接数；技术栈不变不等于运行架构不变。

## 3. ADR-02：模块化单体，按运行职责拆分

**选择：**单仓库保留账号、邮箱、日程、工作台、招聘、发票、Agent 等业务模块。首先形成 API、调度、I/O Worker、OCR Worker 四类启动职责，同一业务版本复用内部函数和存储接口。

API 要低延迟，模型/邮箱任务主要等待网络，OCR 消耗 CPU/内存；这三者分别部署与伸缩有直接收益。日程、行动与发送审核则有强一致性关系，先维持 PG 本地事务比跨服务补偿更简单。

这不是已完成的全面微服务化：角色可以独立扩容，仍共享数据库及部分发布节奏。禁止各进程绕过模块直接改任意业务表，保持数据所有权和版本化任务契约，为以后拆服务留边界。

按页面拆“日历服务/待办服务/工作台服务”会让一次确认动作跨网络和多个事务；按每个 Agent 工具拆服务会放大延迟、权限传播和失败组合。只有当某领域需要独立团队维护、隔离故障域、独立发布，或负载差异无法由 Worker 类型解决，才抽取服务并赋予独立数据所有权。

## 4. ADR-03：Docker 先解决交付一致性，K8s 解决多节点运行

**Docker 选择理由：**锁定 Node、原生 canvas、PDF/OCR 依赖与语言包，减少换机器后的差异；区分 API 与 OCR 镜像/资源配额；使回滚基于镜像 digest。API 镜像首期可带前端静态产物，OCR 重依赖单独构建目标，没必要为静态页面立即购买 CDN。

S1 在单主机上以 Compose 管理上述应用角色和反向代理，数据库与对象存储外置。现有 Compose **仅启动 RabbitMQ**，不具备该方案的内容。Compose 能提供进程重启和资源配置，但不提供跨主机调度、节点故障迁移或自动容量管理。

应用主机优先评估CompShare华北二A/上海二B的Ubuntu**系统镜像虚机**无卡8核16G，官方有在系统镜像安装Docker/Compose的说明。平台交付的容器镜像不等同于可控制宿主机：不假设能嵌套Docker、运行kubelet或配置完整容器网络。无卡需从已有按量GPU实例启动，首次创建和库存约束计入可复现部署及成本；普通业务无需持续支付GPU运行费用。2核4G无卡规格不能直接承接原4核8GiB方案的全部并发/内存上限。

S2 选 Kubernetes/UK8S 的依据是：同一主机容纳不了期望故障冗余、需要滚动发布与自动恢复、不同 Worker 需要独立伸缩。Deployment、资源 requests/limits、探针、HPA、PDB 和节点调度有明确用途。代价是至少要承担节点余量、控制面/入口/观测开销、网络及版本升级工作。

目前没有取得CompShare自带托管K8s或其既有实例可直接加入UK8S的官方确认，故UK8S属于UCloud补充方案。迁移的是镜像和外置状态，不是无条件把原实例注册成节点；不为留在同一控制台而自建缺少运维保障的K8s控制面。

| 方案 | 适合 | 本项目决定 |
| --- | --- | --- |
| 裸机进程 + systemd | 最小单机服务且环境差异很小 | 可用于临时开发；正式交付选镜像以固定 OCR 等依赖 |
| Docker Compose | 小规模、可接受主机故障停机、角色隔离 | S1 默认方案 |
| 托管 Kubernetes | 多节点、独立扩缩容、滚动部署与调度 | S2 目标，先完成分布式正确性 |
| 自建 Kubernetes 控制面 | 已有运维团队/特殊环境 | 当前收益不足，优先把精力用于业务与恢复 |
| FaaS/纯函数计算 | 短时、无持久连接、平台限制合适的任务 | 不作为主运行时：IMAP IDLE、长模型调用、OCR大依赖及SSE需核查超时/网络限制；未来可用于独立短定时任务 |

K8s 并不自动提供数据库 HA、SMTP exactly-once 或业务幂等。HPA 扩的是 Pod，节点扩容扩的是可调度资源，供应商额度限制的是有效处理速率，三者必须同时设计。

## 5. ADR-04：PostgreSQL 是权威存储，逐步整理关系表

**选择：**PG 保存账号、会话、邮箱元数据与设置、日程/待办、工作台行动、任务、外部操作账本和审计索引。沿用现有 JSONB 兼容载荷过渡，但经常并发更新、需要唯一约束或按时间查询的实体逐步拆成有版本列的关系表。

PG 事务能把“确认行动、写日程、登记后续同步任务”一起提交；行级锁、唯一约束、条件更新与 `SKIP LOCKED` 足够支撑早期可靠执行。代价是业务和任务共享 CPU/I/O，需要分连接池配额、索引、短事务、任务清理与容量监测。大量 JSONB 整包改写会增加锁冲突与 WAL，不作为永久全库模型。

| 替代方案 | 取舍 |
| --- | --- |
| MySQL | 同样可实现事务和任务领取，不是技术上不能做；现有 PG 接入、JSONB 使用和潜在 pgvector 使迁移到 MySQL 缺乏收益 |
| MongoDB | 灵活文档并不能消除跨行动/日程/审核的一致性要求；多文档事务及关联查询会引入另一套复杂度 |
| SQLite/sql.js/JSON + 共享盘 | 适合本地模式；共享盘不能修复各进程内存快照、整文件覆盖和原子事务缺失，不用于多节点权威状态 |
| 每个模块独立数据库 | 当前会破坏已有紧密事务边界；将来按服务独立所有权和团队边界再评估 |

托管 PG 优先于在应用集群里自建数据库：备份、监控、故障切换能力更容易标准化，但仍要验证版本、连接限制、PITR、TLS、可用区和恢复演练；“托管”不等于满足目标 RPO/RTO。

公开CompShare资料尚不足以确认托管PG产品及到UCloud PG的默认私网互通，因此PG优先以UCloud标准云合适服务补齐。应用主机到数据库的安全、可支持网络是准入条件；不满足时应用也放同VPC的UHost，模型仍优先ModelVerse。不要为了平台优先改用对象存储/云存储Pro保存数据库目录，或把公网5432暴露作为默认补救。自管PG需独立预算备份、补丁、值守与故障演练，不能沿用托管承诺。

## 6. ADR-05：首期 PG 持久任务，RabbitMQ 为可选传输层

**选择：**同库事务写 `jobs`，Worker 通过短事务领取并持有可续约租约。业务与任务同库时不需要为了“outbox 模式”重复建一套相同记录；当任务要发布到 RabbitMQ 或另一个系统时，再同事务写 outbox，由发布器可靠投递。

当前业务尚无同版本任务吞吐测量，先省去独立 Broker 的固定成本、备份和故障切换。PG 已是必需状态服务，能够避免“业务已提交但任务未登记”的双写窗口。**这并不意味着手写一个循环即可生产可用**：完整状态机、幂等、租约、延迟重试、死信/人工处理、清理、指标与故障测试都是必做工作，见 [03](03-state-and-task-reliability.md)。实现时评估成熟 PG 队列库对事务复用、取消和租约的支持；无论自建或使用库，都以相同验收标准为准。

| 方案 | 优点 | 本项目的代价/决定 |
| --- | --- | --- |
| PG jobs | 同库原子登记，少一套基础设施，可按租户和状态查询 | 领取/心跳/清理占数据库资源；S1/S2初期默认 |
| RabbitMQ | 消费确认、流控、路由、独立积压承载，已有 amqplib 基础 | 仍需 PG 操作账本/outbox；需 publisher confirms、重试、DLQ及Broker HA；当前代码不完整 |
| Redis + BullMQ | Node 生态成熟，延时任务与重试方便 | 引入必须持久可靠的Redis以及PG→Redis双写；已有Redis缓存用途不能替代任务可靠性评估 |
| Kafka | 大规模事件日志、分区顺序、多消费者重放 | 目前是有限生命周期任务，不是高吞吐事件流平台；运营与消费语义成本偏高 |
| Temporal等工作流引擎 | 长期工作流、计时器、版本化恢复能力强 | 现阶段可由持久行动状态和任务满足；若多日、多系统补偿分支持续增加，再比较研发维护成本 |

RabbitMQ 的引入条件是：经过索引、批量领取、归档及连接池隔离后，PG任务负载仍破坏业务延迟目标，或者明确需要复杂路由/消费者隔离。不能只因排队增长就引入 MQ：若受模型429限额约束，更换队列不会增加有效吞吐。已有 RabbitMQ 基础也可在实际团队运维成本更低时被选为首期替代，但必须完成同样的持久账本和投递保障，不能直接使用现有故障回退行为。

引入后，PG仍是任务真相，MQ通知可重复；outbox发布使用确认，业务提交后再ack，未完成任务靠PG对账补投。不要把`persistent: true`等同于已确认投递，不把一次消费者确认说成外部副作用仅执行一次。

## 7. ADR-06：Redis 按共享热点和限流需要引入

当前代码的验证码与会话使用 Redis/内存，JWT还需检查服务端 `jti`，因此**当前代码不能仅关闭 Redis 后直接扩 API 副本**。

目标S1默认将会话、撤销版本、验证码摘要/消费、低频配额计数放PG，带过期索引和清理；会话touch节流，避免每个请求都写一次。此改造未完成前，若先部署当前会话路径，必须有可靠共享Redis且移除生产内存回退；它不是本方案声称“Redis可省”的已达条件。

当认证/限流写入实测显著挤占PG，或有命中率高、允许短暂陈旧的热点读缓存时引入Redis。令牌桶使用原子操作；缓存key含用户、邮箱及版本，设置TTL和删除策略，禁止缓存命中绕过授权。

Redis宕机：普通缓存可旁路读PG；安全限流可进入更保守限制或拒绝动作，不能放开；如果它承担活跃会话唯一状态，应明确重新登录或拒绝鉴权，不能直接接受JWT。发送授权、发送结果、任务完成状态不以Redis为唯一证据，分布式锁也不代替PG条件提交与外部unknown保护。

## 8. ADR-07：优先 CompShare 云存储的私有 US3 接口，元数据放 PG

邮件附件、简历和材料在多副本间必须可读取，且大小与保留周期独立于应用发布。对象存储适合这些不可变二进制；PG保存对象key、所属用户/邮箱、摘要、大小、版本与状态。对象必须鉴权后读取或签发短时受限URL，不开放公共桶。

优先评估CompShare华北二A/上海二B的云存储。其官方文档明确为对象存储并链接US3 S3说明，与当前`server/infra/oss.js`的S3 SDK/path-style方向一致。云存储Pro则是其他区域的POSIX文件存储，适合训练数据集/Checkpoint，当前附件业务没有为它额外付费的必要，也不能将其名称视为S3兼容证明。原件使用SDK访问私有对象，不要求将对象桶挂成文件目录。

[US3官方S3说明](https://docs.ucloud.cn/ufile/s3/s3_introduction)已明确V4签名、path-style与账号/key对应约束，同时说明不支持Versioning、ETag不同、PutObject最大1GB、ACL/lifecycle部分地域受限、内网不支持HTTPS。因此默认以**不可变对象key + PG内容版本/哈希 + 独立保留备份**实现恢复，不依赖桶版本；选择经验证的HTTPS接口，不为“同地域内网”默降HTTP。若有大小超过简单上传限制的需求再实现分片，业务默认仍限定小附件。特定endpoint、凭据最小权限、匿名拒绝、Range、上传/删除与备份恢复均需实连；文档明确支持不等于当前SDK与实际账户已验证。

本地盘会绑定实例生命周期；NAS虽然共享目录，但带来挂载、权限、容量及快照管理，且不能修复JSON并发写。MinIO适合特定私有部署或开发兼容测试，首期云上自运维没有明显收益。数据库只保存元数据，避免大文件撑大WAL、备份和事务。

成本包括容量、请求、流量、版本及备份。小规模先由API鉴权代理附件，业务增长后再按带宽/CPU/安全需求采用受限直传和短期下载URL；不得把“有CDN”作为私有附件访问控制。

## 9. ADR-08：检索先评测，pgvector 后置

当前RAG能分块、关键词/可选embedding混合检索和返回引用，但查询主要在Node读取块后计算相似度；创建过可选vector列不等于已启用向量索引加速。

首期保留附件、页码、版本和租户过滤，先建立中文简历与申请材料评测集，测召回、引用正确率、延迟和每次查询成本。明确字段/关键词能解决的查询不用embedding；模型不应对简单的日程列表做向量检索。

当片段数量使扫描延迟超标，且向量确实提升召回时，优先同库pgvector，避免立即增加向量库。必须核实托管PG扩展权限、维度、embedding模型版本和索引策略；中文分词/关键词策略需评测，默认英文全文检索配置不能直接代表中文检索质量。迁移向量模型先建新版本索引再切换，不混用不同维度或空间。ANN检索的权限过滤和召回率共同测试，权限失败不能靠事后删结果掩盖。

独立Milvus/Qdrant等只在向量规模、性能或独立运维需求值得拆分时引入；Elasticsearch/OpenSearch只在全文搜索复杂度和数据规模需要时评估。Reranker增加延迟与调用费用，有对照收益再启用。初期不自托管GPU模型：邮件/工具任务以按量API更灵活；只有持续利用率、数据边界、质量和全成本测算同时支持时才评估GPU。

需要embedding时先评估ModelVerse官方向量接口，聊天模型与embedding模型独立配置；例如官方`text-embedding-3-large`默认3072维，与现有可选1536维列不兼容，不能只改Base URL就上线。PDF先提取文本层、必要时本地Tesseract OCR；ModelVerse DeepSeek-OCR作为困难页面的按需候选，它的图片→Markdown示例不能替代PDF拆页、字段校验、权限与证据链。两项均有真实质量与成本收益后启用，详见06。

## 10. ADR-09：保留明确 Agent 工具契约，不先更换编排框架

已有OpenAI兼容Chat Completions、JSON结构化输出、工具调用、trace与人工审核可以继续复用。先把模型结果作为待验证建议，服务端检查结构、权限、当前实体版本和动作授权，再执行工具。复杂多步任务靠持久状态恢复，重启不重跑已完成副作用。

LangChain等框架、图编排、工作流平台可降低特定复杂流程的开发成本，但引入框架不自动获得幂等、权限或恢复能力。当前应优先整理工具输入输出、步骤预算、超时、失败分类、来源引用与版本记录，之后按需要评估框架适配收益。

模型端点保持可配置；本次优先选ModelVerse按量API作为邮件提取、小D工具调用和按需embedding的候选服务。它与现有Chat Completions协议方向一致，减少接口重写和模型运维，但必须逐型号验证JSON输出、工具调用、上下文限制、usage与错误语义，不能从“OpenAI兼容”推断全部模型能力相同。先比较平台内满足契约的模型，再在显式授权下选择其他服务；不改用户已保存配置，不以优先原则自动迁移历史数据或模型调用。

CompShare的Coding/Agent套餐、现成Agent托管和API模型服务是不同产品。Daylight需要多租户后台调用、独立审批和任务状态，首期按量API更容易按任务核算；套餐允许范围与预算需另验，不能把开发工具套餐或现成聊天Agent当成整个Daylight的可部署后端。记录模型/提示词/模板版本与usage；缺usage或价格记未知。只自动重试可确认无业务副作用的阶段；备用模型须经过质量、隐私及预算配置，不能静默把私人邮件转发给另一个服务商。

## 11. ADR-10：观测能力必需，观测平台按规模选择

首期必需：结构化脱敏日志、可持久查询的任务/操作账本、HTTP与任务延迟/错误/资源指标、告警渠道及恢复步骤。复用业务trace标识，用OpenTelemetry传播API→任务→工具的关联；记录输入摘要、来源、授权和工具结果，不收集模型私有思维链，也不把邮件正文或API Key写入遥测。

S1优先使用已有可用的云日志/指标能力或小型采集部署；S2可使用Prometheus格式指标与Grafana看板。Loki、Tempo、独立Collector集群按日志量、采样、留存与查询需求引入，不一开始自建全套观测集群。用户ID/邮箱ID/jobId用于有权限的日志检索，不作为高基数指标标签。

选择依据是故障定位时能回答“任务停在哪、为什么、是否执行过外部动作、下一步如何恢复”，而不是监控页面数量。告警先配置接收责任人与处理办法；无人响应的告警不算运营保障。

## 12. ADR-11：CompShare 优先，按能力补齐云基础设施

| 能力 | 首选与补充关系 | 不可省略的核验 |
| --- | --- | --- |
| 文本/工具模型 | CompShare ModelVerse按量API首选 | 每型号JSON/tools/usage、数据处理条款、RPM/TPM/并发、价格和余额、错误及服务承诺 |
| 计算 | 首选前两区无卡Ubuntu VM 8核16G；准入不满足以UHost补齐 | GPU首次创建/关机无卡流程、常驻/配额/库存、CPU架构、网络、回收与真实总成本 |
| 容器编排 | Compose用于S1；UCloud UK8S按需补齐S2 | CompShare平台容器不等于K8s，现有实例入集群支持不可假设；CNI、伸缩、升级另核验 |
| 业务数据库 | UCloud具备所需能力的托管PG补齐，CompShare未确认此能力 | 安全连通、PG版本、HA、TLS/CA、PITR、连接数、扩展、备份导出 |
| 附件 | 首选CompShare云存储的私有US3接口；必要时标准US3补齐 | bucket和key同属账号、S3 V4/HTTPS、私有权限、不可变key备份、下载流量 |
| 网络 | CompShare支持区域的公网/主机防火墙；UCloud VPC/ULB按部署补齐 | 前者仅外网访问控制不等于VPC互通；TLS、SSE、SMTP出网、PG安全路径和故障边界 |
| 密钥与备份 | 可验证的受控注入、密钥服务及独立备份位置补齐 | 不假定统一账号/密钥/权限；备份独立故障域、余额、恢复密钥可用性 |
| 可选缓存/消息 | 需要时选择符合协议的Redis/RabbitMQ服务 | 未确认CompShare自带托管服务；持久性、故障切换、TLS、额度、价格独立核验 |

优先同地域并在明确支持时用私网减少延迟与流量费，但CompShare归属UCloud不证明跨产品VPC天然互通。为打通数据库而增加专用网关/隧道也有费用、故障和运维责任，只有验证收益后另行采用；默认不为留在某个平台强加一套跨云网络。业务数据采用PG、对象key和版本化任务协议，保留可导出性。

CompShare公开[框架协议](https://www.compshare.cn/docs/overview/serviceagreement/frame)第1.2.1有“不对任何服务可用性、可靠性做出承诺”的表述。本次不对具体订单作法律结论，采购前要核验该条的适用产品及是否另有有效服务约定；系统SLO/RTO/RPO是设计与自测目标，不能继承其他UCloud产品SLA。

DNS、域名与HTTPS是公网交付必需；CDN、WAF、专线、服务网格、多地域双活只有在访问分布、风险、带宽或恢复目标提供依据后再采购。基础网络访问控制和TLS仍是默认设计，不因暂不采购WAF而省略。

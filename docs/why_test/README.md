# Daylight 云原生架构、选型与部署设计

设计日期：**2026-10-17（北京时间）**。初版代码核查基线：`ada690ccf228`；本次按“优先使用优云智算”修订，工作区基线为 `74d6b917f1a0`，分支 `feat/real-mail-cost`。

**本目录是待评审、待实施的方案，不是部署完成报告。** 本次仅阅读代码、已有文档及公开技术资料并编写设计，没有创建云资源、构建或启动容器、修改业务代码、迁移数据、读取实际业务数据、调用邮箱/模型或发送邮件。目录名中的 `test` 不表示已经执行云端测试。容量、阈值和恢复目标均为设计假设；明确引用的公开价格仅用于带日期的算例，不代表实际订单或总账单。

## 1. 推荐结论

Daylight 应以**模块化单体代码库 + 按负载拆分的运行进程 + PostgreSQL 权威状态 + 对象存储**作为起点，再按可用性和容量需要演进到 Kubernetes。不要先按页面拆十几个微服务：邮件、工作台、日程和确认动作存在紧密事务关系，而 API、网络等待任务、OCR 的资源差异已经足够明确，值得先隔离。

- **优先优云智算：**模型首先评估 CompShare ModelVerse 按量 API；应用主机首先评估华北二A/上海二B的 Ubuntu 系统虚机无卡 **8核16G**，用 Docker Compose 运行四类角色；附件首先评估该平台云存储的私有 US3/S3 接口。模型、计算和对象存储都有项目用途，按对应契约验证后采用。
- **必要能力补齐：**PostgreSQL 继续承担权威状态。当前公开资料尚不能确认 CompShare 提供托管 PG、用户可管理的 K8s/ULB，或默认与 UCloud VPC 互通；这些能力按需由 UCloud 标准云补齐。若 CompShare 到外置 PG 的安全网络、常驻条件或恢复能力不成立，应用主机改用同 VPC 的 UHost，同时保留 ModelVerse 优先，不能为供应商优先牺牲数据正确性。
- **首期可靠任务：**在 PostgreSQL 中原子保存业务变更和任务登记，通过短事务领取、租约、重试与人工处理状态恢复任务。它是需要新建和验证的持久任务机制，当前进程内队列不满足要求。
- **运行边界：**API、调度器、I/O Worker 和 OCR Worker 分开运行，复用业务模块和版本；最初可在同一主机上隔离资源。外部调用在数据库事务之外进行。
- **进入多节点阶段：**共享状态、并发与副作用保护通过后，按需采用 UCloud UK8S/Kubernetes 管理副本、滚动发布和资源调度；它是补充编排方案，不是已证实的 CompShare 内置能力。按可运行积压、资源负载及 ModelVerse/邮箱额度扩缩容。
- **按证据引入：**Redis 用于确有负载收益的共享限流/缓存；RabbitMQ 用于数据库任务队列已出现调度瓶颈或更强路由隔离需求；pgvector 用于检索质量与规模需要。三者均不是本轮新生产设计的默认前置。
- **首期暂不引入：**Kafka、独立向量数据库、服务网格、GPU 模型集群、多地域双活、按业务页面拆分的独立微服务。每项保留重新评估条件。

这条路线的取舍是：用较少的基础设施降低固定成本与故障组合，但需要把事务、任务状态机和运维能力做完整。单主机试点有停机边界；K8s 也只有在状态与故障机制正确后才能产生可用性收益。

优云智算无卡模式是已有按量 GPU 实例关机后的启动选项，不是已证实可直接创建的普通 CPU SKU；首次 GPU 创建、无卡配额和重建步骤需核验。平台“云存储 Pro”是文件存储，不能当作对象存储或数据库备份。公开资料、接口契约和实施前检查分别见04、06；用户现有模型配置不会因这份方案被改写。

## 3. 四个阶段及准入原则

| 阶段 | 部署与定位 | 必须完成的条件 |
| --- | --- | --- |
| S0 当前代码 | React + 同一 Node 进程；已有可选 infra 接入 | 如实记录能力；不能把依赖接通等同于多副本正确 |
| S1 可恢复云端试点 | 首选 CompShare 无卡 Ubuntu VM + Docker，PG/US3外置，模型用ModelVerse；主机不满足准入时以UHost补齐 | 核验创建/无卡/常驻/网络与存储；数据权威统一、任务恢复、真实依赖验证、异机恢复；接受单应用主机停机 |
| S2 多节点运行 | 按需使用UCloud UK8S补齐编排、跨节点副本、负载入口与受控弹性；继续优先ModelVerse | 不假设原CompShare实例能直接加入集群；多实例隔离/幂等、节点故障、发布和容量验证；按承诺选择数据库HA |
| S3 按测量优化 | Redis、RabbitMQ、pgvector、专用节点等按瓶颈加入 | 每次增加组件都须有性能/成本/可靠性对照，不以组件数量代表成熟度 |

S1 是成本受控的演进阶段，不是项目的规模上限或商业上线认证。若首次正式服务就要求持续可用，应在状态改造后直接按 S2 的故障域要求部署，而不是先对外承诺 S1 不具备的能力。

## 4. 与既有材料的关系

本设计遵循 [项目约定](../../AGENTS.md)、[现有使用入口](../../README.md) 和 [最新状态记录](../../STATUS.md)，细化 [云原生建设基线](../cloud-native-roadmap.md)。[DEPLOY.md](../../DEPLOY.md) 仍描述现有启动与依赖配置方式。

本目录对未来方案有三处明确调整，评审时不要混用旧建议：

1. [旧云原生与 RAG 文档](../cloud-native-and-rag.md) 中的“MQ 故障回退进程内队列”“Redis 故障仍仅靠 JWT”不能作为生产容灾方案。当前登录还校验服务端会话；新方案要求共享会话和持久任务，不静默回退。
2. 旧文档中的 Redis/RabbitMQ 默认拓扑改为按需启用，首期改用 PG 持久任务与共享会话。这是**设计建议的变化**，不是声称当前代码已经支持此运行模式。
3. 旧文档的 JSON“回退”仅可保留在显式开发模式；生产数据库失效要暂停相应操作、告警和恢复。当前部分普通存储路径尚未满足此要求。

业务现状以当前代码和 STATUS 最新条目为准。例如当前智能招聘、发票保留内置入口与历史工作台兼容，不能从旧路线中的页面描述推定需要新建独立服务。本次没有改变功能或开发约定，因而保持根 README、STATUS 和 AGENTS 不变。

## 5. 评审时需要落实的输入

默认按个人账号拥有邮箱、工作台可引用自己邮箱的现有边界设计，暂不声称已有企业组织共享权限。人数、邮箱数量、同步新鲜度、OCR 页数、模型预算、停机容忍度尚无同一版本的容量实测，因此不写成已知需求。

后续实施前需确认：首批活跃邮箱与峰值负载、月预算、对外可用性目标、CompShare区域/无卡配额/创建成本及常驻条件、ModelVerse具体模型的JSON与工具契约/额度、US3账号与私有访问、外置PG的安全网络和恢复能力。公开文档已核实与真实服务已验证分开记录；验证方法及决策门槛见04、05、06。
